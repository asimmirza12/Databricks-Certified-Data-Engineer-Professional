The idea

The idea in plain English

A file format is the agreed layout of the bytes inside a file. It decides three big things: can a human read it, does it carry its own schema, and how much must be read to answer a question.

Formats fall into two families:

  • Row-based formats store one whole record after another. Good for writing records as they happen. CSV, JSON and Avro are row-based.
  • Columnar formats store all values of one column together, then the next column. Good for analytics, because a query that needs 2 columns out of 12 can skip the other 10. Parquet is columnar.

Columnar files also compress well (shrink by storing repeats cleverly), because values in one column look alike.

Then there are table formats: Delta Lake and Apache Iceberg. They are not a new way to lay out bytes. They are Parquet data files plus a log of metadata that records which files make up the table, their column statistics, and every change. That log is what lets them skip whole files and handle updates safely.

Think of a class's exam results. Row-based is a stack of report cards: one card per student, all subjects on it. To find the class average in maths, you flip through every card. Columnar is one sheet per subject: grab the maths sheet and you are done. A table format adds a librarian's index card listing which sheets exist and the lowest and highest score on each, so you can skip sheets that can't contain what you want.

In code

Reading each format. Note which ones need extra options, because the file does not describe itself:

base = "/Volumes/bike_shop/raw/landing"

# CSV: plain text. You must say whether line 1 is a header; types are guessed or given.
csv_df = spark.read.option("header", True).option("inferSchema", True).csv(f"{base}/rides_csv/")

# JSON: text with field names on every record. Nested data is allowed.
json_df = spark.read.json(f"{base}/rides_json/")

# Parquet and Avro: binary files that carry their own schema. No options needed.
pq_df   = spark.read.parquet(f"{base}/rides_parquet/")
avro_df = spark.read.format("avro").load(f"{base}/rides_avro/")

# Binary files (images, PDFs): one row per file with path, size and raw bytes
pics = spark.read.format("binaryFile").load(f"{base}/bike_photos/")

Tables. On Databricks, Delta Lake is the default table format; Iceberg must be asked for:

-- Delta is the default: no USING clause needed
CREATE TABLE bike_shop.silver.rides AS
SELECT * FROM read_files('/Volumes/bike_shop/raw/landing/rides_csv/', format => 'csv', header => true);

-- An Iceberg table must say so explicitly
CREATE TABLE bike_shop.silver.rides_iceberg USING ICEBERG AS
SELECT * FROM bike_shop.silver.rides;

-- Table formats allow safe changes to single rows
UPDATE bike_shop.silver.rides SET price = 9.00 WHERE ride_id = 'r0042';

Options

What if I change this?

ChangeEffect
Store analytics data as CSV instead of ParquetFiles are several times bigger and every query reads every column. Slower and more expensive.
Read CSV with inferSchemaSpark scans the data to guess types. Convenient, but slower, and a guess can change between files.
Read CSV without headerThe column names become _c0, _c1… and the header line is treated as a data row.
Plain Parquet folder → Delta tableSame data files, plus a transaction log: safe updates and deletes, history, file skipping from stored statistics.
Delta table → Iceberg table (USING ICEBERG)Useful when outside tools need Iceberg. Delta stays the recommended default on Databricks.
Keep Delta but let Iceberg tools read it (UniForm)Iceberg metadata is generated alongside Delta's, without rewriting the Parquet files. Details in module 02.

Family

Row-based

CSV, JSON, Avro. Whole records together. Easy to append, costly to analyse.

Family

Columnar

Parquet (and ORC). Columns together, compressed. Fast to analyse.

Family

Table formats

Delta Lake, Iceberg. Columnar files plus a metadata log for safe changes and skipping.

Exam traps

Exam traps and look-alikes

Trap

"Delta is a file format like Parquet." Not quite: Delta's data files are Parquet. Delta adds the transaction log on top. Same for Iceberg with its metadata files.

Trap

Writing CREATE TABLE … AS SELECT without USING on Databricks gives a Delta table, not Parquet or Iceberg.

Don't confuse

Avro (row-based, binary, great for streaming messages) vs Parquet (columnar, great for analytics). Both carry a schema; they suit opposite jobs.

Don't confuse

Compression makes files smaller. Column pruning skips columns you didn't ask for. File skipping skips whole files using statistics. Different savings that stack.

Check yourself

Quiz

1. A query needs 2 of a table's 40 columns. Which layout reads the least data?

Columnar files keep each column together, so the reader fetches just the 2 columns needed. Row-based formats must read whole records.

2. What does Delta Lake add on top of Parquet files?

Delta's data is stored as Parquet. The log is what enables safe updates, history and skipping files.

3. On Databricks you run CREATE TABLE t AS SELECT … with no USING. What format is t?

Delta Lake is the default table format. Iceberg needs USING ICEBERG.

4. Which format is a common choice for messages flowing through Kafka?

Avro is compact, row-based and carries a schema, which suits writing one message at a time. Parquet and table formats suit analytics on stored data.

Wrap-up

Key takeaways

  • Row-based formats (CSV, JSON, Avro) keep records together; columnar (Parquet) keeps columns together.
  • Columnar files compress well and let queries skip unneeded columns.
  • Delta Lake and Iceberg are table formats: Parquet files plus metadata for safe changes and file skipping.
  • Delta Lake is Databricks' default table format; Iceberg is chosen with USING ICEBERG.
