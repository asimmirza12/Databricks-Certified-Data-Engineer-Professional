The idea

The idea in plain English

Every app, website and machine creates data: facts written down as they happen. A bike rental shop records every ride. Who rode, which bike, how long, how much they paid.

That raw data is messy. It sits in many places. Some records are broken. Nobody can answer a simple question like "how much did we earn last week?" by looking at it directly.

Data engineering is the work of moving data from where it is created to where people can use it, and cleaning it on the way so they can trust it. A data engineer is the person who builds and runs that path.

The path itself is called a data pipeline: a series of steps that run again and again, usually on a schedule. A classic pipeline has three steps, known as ETL:

  • Extract: copy data out of the place it was created (the source).
  • Transform: clean it, fix it, and reshape it. Remove broken rows. Convert units. Join related data.
  • Load: save the result somewhere people can query it (ask it questions, like "total revenue last week"), usually a table (rows and named columns, like a tidy spreadsheet).

The people who use the result are consumers: analysts building dashboards, data scientists training models, and apps showing numbers to customers.

Think of a city's water system. Rain falls in many places (sources). Pipes collect it (extract). A treatment plant filters out dirt (transform). Clean water reaches every tap (load). People turning on a tap never think about the plant, until it breaks. A data engineer runs the treatment plant for data.

Code

In code

You do not need to understand every word yet. Later lessons explain each piece. For now, spot the three steps. Here is the same pipeline in Python, using PySpark (the Python way to talk to Apache Spark, the engine Databricks runs on):

# EXTRACT: read the raw ride files the app drops into storage each day
raw = (spark.read
       .option("header", True)            # first line holds column names
       .csv("/Volumes/bike_shop/raw/landing/rides/"))

# TRANSFORM: keep only rides with a real, positive price
from pyspark.sql import functions as F

clean = (raw
         .withColumn("price", F.col("price").cast("decimal(8,2)"))  # text -> number
         .filter(F.col("price").isNotNull() & (F.col("price") > 0)))

# LOAD: save the result as a table anyone with access can query
clean.write.mode("overwrite").saveAsTable("bike_shop.silver.rides")

And the same idea in SQL (Structured Query Language, the standard language for asking tables questions). read_files reads files straight from storage:

-- Extract + transform + load in one statement
CREATE OR REPLACE TABLE bike_shop.silver.rides AS
SELECT ride_id, bike_id, started_at,
       CAST(price AS DECIMAL(8,2)) AS price
FROM read_files('/Volumes/bike_shop/raw/landing/rides/',
                format => 'csv', header => true)
WHERE CAST(price AS DECIMAL(8,2)) > 0;   -- NULL > 0 is not true, so missing prices drop too

-- What a consumer runs afterwards
SELECT SUM(price) AS revenue FROM bike_shop.silver.rides;

The name bike_shop.silver.rides has three parts: catalog, schema, table. You will meet that idea in 00-11 Unity Catalog basics, and "silver" in 00-12 Medallion architecture.

Options

What if I change this?

ChangeEffect
Skip the transform (cleaning) stepThe pipeline is faster to build, but broken rows reach the table. Every number built on it can be wrong, and nobody may notice.
Run once a day → run every few minutesFresher numbers, but more compute cost. Going all the way to "as soon as data arrives" is streaming (lesson 00-04).
Reload all data every run → load only new dataMuch cheaper as data grows. But the pipeline must remember what it already loaded, or it loads files twice (you saw this risk in the demo).
Transform before loading (ETL) → load raw first, transform inside the platform (ELT)Keeps an untouched raw copy you can re-process later. This is the usual pattern on Databricks.
Add a data quality check that stops the runBad data never reaches users, but the dashboard goes stale until someone fixes the problem. Later lessons show how to warn, drop or stop.

Who uses the data

Data engineer

Builds and runs the pipelines. Cares that data arrives on time, complete and correct.

Data analyst

Asks business questions with SQL and dashboards. Needs clean, well-named tables.

Data scientist

Builds models that predict things. Needs lots of reliable history.

ML engineer

Puts models into production. Needs fresh data feeding them every day.

App developer

Creates much of the source data, and sometimes shows results back to users.

Platform admin

Sets up access, cost limits and security for everyone else.

Exam traps

Exam traps and look-alikes

The Professional exam does not ask "what is ETL?". It hides these basics inside harder questions, so the words must feel natural.

Trap

"The pipeline ran successfully" does not mean the data is right. A run can succeed and still load broken rows. Quality checks are a separate thing you add on purpose.

Trap

Re-running a pipeline should not change the result if no new data came in. A pipeline with this property is called idempotent. Answers that load duplicates on a re-run are usually wrong.

Don't confuse

Pipeline = the steps that move and change data. Job = the scheduled run that starts work (which can include a pipeline). You will see both in module 01.

Don't confuse

ETL cleans before loading. ELT loads raw data first, then cleans inside the platform. Databricks setups are usually ELT.

Check yourself

Quiz

1. In ETL, what does the "T" step do?

Transform is the cleaning and reshaping step: removing broken rows, converting types, joining data. Copying out is Extract; saving is Load.

2. The bike shop's dashboard shows negative revenue for one day. What most likely happened?

If the pipeline had not run, you would see old or missing numbers, not negative ones. Negative totals point to bad rows that slipped through without a cleaning or quality step.

3. You run the same pipeline twice with no new data, and the row count doubles. Which word describes what the pipeline is missing?

An idempotent pipeline gives the same result no matter how many times it re-runs over the same input. This one re-adds old data each run.

4. Why do most modern platforms prefer ELT over ETL?

ELT still cleans data, just later and inside the platform. Keeping the raw copy means a bug in your cleaning logic can be fixed and re-run over history.

Wrap-up

Key takeaways

  • Data engineering moves data from where it is made to where people use it, and makes it trustworthy on the way.
  • A pipeline is a repeatable set of steps: extract, transform, load (or load first, then transform: ELT).
  • A run that "succeeds" can still load wrong data. Cleaning and quality checks are deliberate design choices.
  • Good pipelines are safe to re-run (idempotent) and only process what is new.
