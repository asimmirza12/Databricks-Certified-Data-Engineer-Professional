The idea

The idea in plain English

Unity Catalog is Databricks' system for organising and governing data. Governance means controlling who can see and change what, and keeping a record of it.

It arranges everything in a tree. At the top is a metastore: one per cloud region, shared by the workspaces in that region. Inside it:

  • A catalog: the biggest folder, often one per team, project or environment (like bike_shop or dev).
  • A Unity Catalog schema (also called a database): a folder inside a catalog, like silver. Not the same as a table's column schema!
  • Objects inside a schema: tables, views (saved queries), volumes (governed files) and functions.

So every table has a three-part name, the three-level namespace: catalog.schema.table, like bike_shop.silver.rides.

Tables come in two kinds. A managed table's files are stored and looked after by Unity Catalog: drop the table and its data is deleted (after a short recovery window). An external table points at files in a storage path you manage: drop it and only the registration goes; the files stay.

Access works by privileges that you GRANT to users or groups. To read a table you need three: USE CATALOG on its catalog, USE SCHEMA on its schema, and SELECT on the table. Privileges granted on a container also flow down to what's inside it.

Unity Catalog is a library. The library building (metastore) has floors (catalogs), each floor has rooms (schemas), and rooms hold shelves of books (tables). To read a book, you need to be let onto the floor, into the room, and allowed that book. A pass for the whole room covers every book in it. The library catalogue also records who borrowed what.

Code

In code

-- Build the tree
CREATE CATALOG IF NOT EXISTS bike_shop;
CREATE SCHEMA IF NOT EXISTS bike_shop.gold COMMENT 'Business-ready tables';

-- A managed table: Unity Catalog chooses and looks after the storage
CREATE TABLE bike_shop.gold.daily_revenue (ride_date DATE, town STRING, revenue DECIMAL(12,2));

-- An external table: you name the storage path (it must sit inside an external location you may use)
CREATE TABLE bike_shop.bronze.partner_rides (ride_id STRING, price DOUBLE)
LOCATION 's3://bike-shop-partner-data/rides/';

-- Let the analysts group read one table: three grants
GRANT USE CATALOG ON CATALOG bike_shop TO `analysts`;
GRANT USE SCHEMA ON SCHEMA bike_shop.gold TO `analysts`;
GRANT SELECT ON TABLE bike_shop.gold.daily_revenue TO `analysts`;

-- Or every table in gold, now and in future (inheritance)
GRANT SELECT ON SCHEMA bike_shop.gold TO `analysts`;

-- Check what has been granted
SHOW GRANTS ON SCHEMA bike_shop.gold;
# Python uses the same three-part names
revenue = spark.read.table("bike_shop.gold.daily_revenue")

# Or set defaults so short names work in this session
spark.sql("USE CATALOG bike_shop")
spark.sql("USE SCHEMA gold")
revenue = spark.read.table("daily_revenue")

Options

What if I change this?

ChangeEffect
Grant SELECT on the table but not USE SCHEMAThe query is still denied. All three levels are needed.
Grant SELECT on the schema instead of each tableEvery current and future table in that schema becomes readable. Less work, broader access.
Grant to a group instead of a personPeople join or leave the group; grants don't need editing. The recommended practice.
DROP TABLE on a managed tableMetadata goes and data files are scheduled for deletion. UNDROP can recover it within the recovery window (7 days by default; verify for your cloud).
DROP TABLE on an external tableOnly the registration is removed. The files stay in your storage.
Write a two-part name (gold.daily_revenue)Spark fills in the current catalog. Fine interactively, risky in jobs where the default catalog may differ.

Exam traps

Exam traps and look-alikes

Trap

"SELECT on the table is enough." It isn't: the reader also needs USE CATALOG and USE SCHEMA on the parents.

Trap

Dropping an external table does not delete its files. Dropping a managed one does (after the recovery window).

Don't confuse

Unity Catalog schema (a container: bike_shop.gold) vs a table schema (its columns and types).

Don't confuse

Metastore (top level, one per region) vs catalog (first level inside it; you create many).

Check yourself

Quiz

1. In bike_shop.gold.daily_revenue, what is gold?

The pattern is catalog.schema.table, so gold is the schema.

2. Which set of privileges lets a group read one table?

Reading needs a privilege at every level of the name: USE CATALOG, USE SCHEMA and SELECT.

3. You drop an external table. What happens to its data files?

For external tables, Unity Catalog only removes its registration. You manage the files.

4. You grant SELECT on schema gold. A new table is created in gold next week. Can the grantee read it?

Privileges are inherited downward, including by objects created later. (They still need USE CATALOG and USE SCHEMA.)

Wrap-up

Key takeaways

  • Unity Catalog names everything catalog.schema.object, under one metastore per region.
  • Managed tables: Unity Catalog owns the files, and DROP deletes them after a recovery window. External tables: you own the files.
  • Reading a table needs USE CATALOG + USE SCHEMA + SELECT.
  • Grants on a container flow down to everything inside, now and later. Grant to groups.
