Medallion architecture

The idea

The idea in plain English

The medallion architecture is a common way to organise tables in a lakehouse into three layers, named like Olympic medals:

  • Bronze: raw data, landed as it arrived, plus a few extra columns like when and from which file it came. Nothing is thrown away, so you can always re-process.
  • Silver: cleaned and checked data. Duplicates removed, types fixed, bad rows dropped or set aside, related data joined. One trustworthy version of each thing (each ride, each customer).
  • Gold: business-ready tables built for a purpose, like daily revenue per town. Often aggregated (rows summed or counted into totals).

Each layer is built from the one before it, so a mistake in gold can be fixed by re-running from silver, and a mistake in silver from bronze. It is a pattern, not a product: Databricks doesn't force it, but its tools are built around it. A common setup is one Unity Catalog schema per layer, like bike_shop.bronze, bike_shop.silver and bike_shop.gold.

Making orange juice. Bronze is the crate of oranges straight from the farm, bruised ones and all, with a label saying which farm. Silver is the washed, sorted, peeled fruit with the bad ones removed. Gold is the bottled juice on the shop shelf, sized for what customers buy. If a batch of juice tastes wrong, you go back to the washed fruit, not the farm.

Code

In code

Three plain SQL steps. (Module 01 builds the same thing as a Lakeflow pipeline that runs incrementally.)

-- BRONZE: land raw files as they are, plus where and when they came from
CREATE OR REPLACE TABLE bike_shop.bronze.rides_raw AS
SELECT *, _metadata.file_path AS source_file, current_timestamp() AS loaded_at
FROM read_files('/Volumes/bike_shop/raw/landing/rides/', format => 'json');

-- SILVER: one clean row per ride, correct types, no broken rows
CREATE OR REPLACE TABLE bike_shop.silver.rides AS
SELECT DISTINCT
  ride_id,
  town,
  CAST(started_at AS TIMESTAMP) AS started_at,
  CAST(price AS DECIMAL(8,2))   AS price
FROM bike_shop.bronze.rides_raw
WHERE ride_id IS NOT NULL AND price IS NOT NULL;

-- GOLD: a business-ready summary
CREATE OR REPLACE TABLE bike_shop.gold.revenue_by_town AS
SELECT town, DATE(started_at) AS ride_date, COUNT(*) AS rides, SUM(price) AS revenue
FROM bike_shop.silver.rides
GROUP BY town, DATE(started_at);

SELECT DISTINCT only removes rows that are identical in every column. Real pipelines usually de-duplicate by key (keep one row per ride_id); module 01 shows how.

Options

What if I change this?

ChangeEffect
Clean data while loading bronzeYou lose the raw copy. When a cleaning rule turns out to be wrong, there is nothing to re-process from.
Build gold straight from bronzeDuplicates and bad rows flow into business numbers (try it in the demo).
Drop bad rows in silver vs set them asideDropping is simple; setting aside (quarantine) lets someone inspect and fix them. Module 03 covers both.
Add more layers (e.g. a "platinum")Allowed: it's a pattern, not a rule. More layers mean more tables to maintain.
Give analysts access to gold onlyThey see clean, agreed numbers and can't build reports on raw data by mistake.

Exam traps

Exam traps and look-alikes

Trap

"Bronze should be cleaned so it's useful." No: bronze keeps raw data on purpose, so you can replay. Cleaning belongs in silver.

Trap

Medallion layers are a naming and design pattern, not separate products or storage systems. All three are ordinary tables, often in separate schemas.

Don't confuse

Silver = one clean row per real thing (each ride). Gold = totals and answers for a purpose (revenue per town per day).

Don't confuse

The medallion architecture (how tables are layered) vs the lakehouse (the overall platform idea, lesson 00-08).

Check yourself

Quiz

1. Which layer keeps data exactly as it arrived?

Bronze stores raw data, usually with extra columns like source file and load time.

2. Where should duplicates be removed and types fixed?

Silver is the clean, validated layer. Bronze stays raw; gold builds on silver.

3. A cleaning rule was wrong for weeks. What makes the fix possible?

Keeping raw data in bronze is what lets you re-run corrected logic over history.

4. Which table belongs in gold?

Gold holds purpose-built, often aggregated tables. Cleaned row-level rides are silver; raw events are bronze.

Wrap-up

Key takeaways

  • Bronze = raw as received; silver = clean and validated; gold = business-ready, often aggregated.
  • Each layer is built from the previous one, so you can always rebuild downstream.
  • Keep bronze raw. Do cleaning in silver. Point analysts at gold.
  • It's a design pattern, commonly one Unity Catalog schema per layer.
