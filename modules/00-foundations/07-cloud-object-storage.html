Cloud object storage

Every table, file and checkpoint you will meet lives in cloud object storage. It is cheap and nearly endless, but it does not behave like the disk in your laptop. Those differences explain many design choices later.

The idea

The idea in plain English

Cloud object storage is a storage service you rent from a cloud provider: Amazon S3, Azure Data Lake Storage (ADLS) or Google Cloud Storage (GCS). You pay for what you store, and it grows without limit.

Storage is split into buckets (Azure calls them containers). A bucket holds objects. An object is a file plus a little metadata, found by its key: its full name, like landing/rides/2026/11/19/rides_0001.json.

Here is the surprise: there are no real folders. The slashes are just characters in the key. Tools show folders by grouping keys that share a beginning, called a prefix. So "rename a folder" really means copying and deleting every object under that prefix, one by one.

Objects are also written whole. You cannot change one line inside an object; you replace the entire object. That is why table formats like Delta Lake write new files and record changes in a log instead of editing files in place.

On Databricks, you normally reach storage through Unity Catalog (lesson 00-11). It keeps the cloud passwords, called credentials, and decides who may read which paths. A volume gives files a friendly governed path like /Volumes/bike_shop/raw/landing/.

Object storage is a giant coat-check room. You hand over a coat, get a ticket with a long number, and the attendant can find it instantly by that ticket. There are no shelves you can rearrange, and to change a button you hand in a whole new coat. If you want "everything from table 12", the attendant reads every ticket starting with 12.

Code

In code

The same storage, addressed three ways. Prefer the governed volume path:

# Raw cloud URIs (each cloud has its own scheme). Unity Catalog checks you may use them.
s3_path   = "s3://bike-shop-landing/rides/2026/11/19/"
adls_path = "abfss://landing@bikeshopstore.dfs.core.windows.net/rides/2026/11/19/"
gcs_path  = "gs://bike-shop-landing/rides/2026/11/19/"

# A Unity Catalog volume: a governed, friendly path to the same kind of storage
vol_path = "/Volumes/bike_shop/raw/landing/rides/2026/11/19/"

# List what's there (dbutils is a Databricks notebook helper)
display(dbutils.fs.ls(vol_path))

# Read it like any other files
rides = spark.read.json(vol_path)
-- Create a managed volume to hold raw files
CREATE VOLUME IF NOT EXISTS bike_shop.raw.landing;

-- List files in it with SQL
LIST '/Volumes/bike_shop/raw/landing/rides/';

Options

What if I change this?

ChangeEffect
Use a volume path instead of a raw s3:// URISame files, but access goes through Unity Catalog permissions and you never handle cloud keys.
Write millions of tiny filesListing and opening each one costs a request, so reads crawl. Bigger files (lesson 00-10, module 05) are faster.
"Rename" a folder with many filesEvery object is copied and deleted. Slow and costly for big prefixes; avoid renaming data folders.
Change one row in a fileThe whole object is rewritten. Table formats handle this for you by writing new files and logging the change.
Use DBFS mounts (old pattern)Deprecated: mounts skip Unity Catalog governance and don't work with serverless. Use volumes or external locations.

Exam traps

Exam traps and look-alikes

Trap

Answers that use DBFS mounts or put access keys in code are almost always wrong on a modern exam. Look for volumes, external locations and Unity Catalog permissions.

Trap

"Just edit the file in place." Object storage can't; table formats write new files and log the change instead.

Don't confuse

Volume (governed files, path /Volumes/…) vs table (governed rows and columns). Both live under a Unity Catalog schema.

Don't confuse

Bucket/container (a cloud storage unit) vs catalog (a Unity Catalog container for schemas). One is storage, one is organisation.

Check yourself

Quiz

1. In object storage, what is a "folder" really?

Storage is flat. Tools group keys that start with the same text and draw them as folders.

2. You need to change one row in a 500 MB file in object storage. What actually happens?

Objects are replaced as a whole. That's why table formats write new files and record changes in a log.

3. What is the recommended way to give Databricks users governed access to raw files?

Volumes are governed by Unity Catalog. Mounts are deprecated and bypass governance; keys in code leak.

4. Why do Spark clusters keep data in object storage rather than on their own disks?

Storage is shared and durable. Clusters can be created and deleted while the data stays put.

Wrap-up

Key takeaways

  • Object storage (S3, ADLS, GCS) holds objects in buckets, found by key.
  • Folders are just key prefixes; renaming means copying every object.
  • Objects are written whole, so table formats add new files instead of editing.
  • Reach storage through Unity Catalog volumes and external locations, not mounts or keys in code.
