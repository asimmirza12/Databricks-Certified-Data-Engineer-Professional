Batch vs streaming

Process data in big scheduled chunks, or continuously as it arrives? The answer is a trade between how fresh the data is and how much compute you pay for.

The idea

The idea in plain English

Data usually arrives as events: small records of something that happened, such as "bike 7 unlocked at 09:14".

Batch processing waits, collects a chunk of events, then processes the whole chunk in one go, usually on a schedule ("every night at 2 a.m."). Between runs, nothing is processed.

Streaming processes events continuously, shortly after they arrive. In Spark, streaming usually works in micro-batches: very small batches, run one after another, each holding only the events that are new since the last one.

The time between an event happening and it showing up in your table is called latency. Streaming gives low latency. Batch gives high latency but can be cheaper, because compute only runs during each scheduled run.

A streaming job remembers how far it got using a checkpoint: a small folder where Spark records which data it has already processed. If the job stops and restarts, it continues from the checkpoint instead of starting over. This is also how a scheduled job can be incremental: process only what is new, then stop.

Batch is a postman who comes once a day and delivers the whole day's letters. Streaming is a pneumatic tube in an office: each message shoots through moments after it is written. The tube is faster, but someone has to keep the air pump running all day.

Code

In code

A batch read: spark.read takes everything that exists right now.

# BATCH: read the whole table as it is now, write the result, finish
events = spark.read.table("bike_shop.bronze.ride_events")
(events.filter("event_type = 'unlock'")
       .write.mode("overwrite")
       .saveAsTable("bike_shop.silver.unlocks"))

A streaming read: spark.readStream plus a checkpoint, so each run handles only new rows. The trigger decides when micro-batches run.

# STREAMING: read only rows that are new since the last checkpoint
new_events = spark.readStream.table("bike_shop.bronze.ride_events")

(new_events.filter("event_type = 'unlock'")
   .writeStream
   .option("checkpointLocation", "/Volumes/bike_shop/silver/checkpoints/unlocks")  # progress is saved here
   .trigger(availableNow=True)    # process the backlog in micro-batches, then stop
   .toTable("bike_shop.silver.unlocks"))

# Other triggers (choose one):
#   .trigger(processingTime="1 minute")   keep running; start a micro-batch every minute
#   (no trigger at all)                   keep running; next micro-batch as soon as the last ends

Running the availableNow version on a schedule gives you batch-style cost with streaming-style "only new data" bookkeeping. You will use this pattern a lot.

Options

What if I change this?

ChangeEffect
No trigger set on a streamMicro-batches run back to back, as fast as possible. Lowest latency for micro-batch, but compute never stops and the constant checking for new files can add storage API costs.
trigger(processingTime="10 minutes")One micro-batch every 10 minutes. Fewer, larger batches; data up to ~10 minutes stale; compute still always on.
trigger(availableNow=True)Processes everything new, then stops. Run it from a scheduled job. This replaced the older Trigger.Once, which is deprecated.
Real-time modeFor sub-second needs, such as fraud checks. Has strict compute requirements (classic compute, specific runtime and settings). Covered later; verify details in the docs.
Continuous trigger (open-source Spark)Not supported on Databricks; the docs point to real-time mode instead.
Delete the checkpoint folderThe stream forgets its progress and re-processes everything from the start. This can create duplicates.
Run on serverless notebooks or jobsAt the time of writing, availableNow is the only trigger supported there. Verify in the docs, since this changes.

Exam traps

Exam traps and look-alikes

Trap

"Streaming means always running." Not necessarily: a streaming query with availableNow runs, processes what's new, and stops. Streaming describes incremental processing, not only uptime.

Trap

Trigger.Once is deprecated. When an answer offers both Once and availableNow for scheduled incremental runs, prefer availableNow.

Don't confuse

Latency = how long until an event is in the table. Throughput = how many events per second you can handle. A system can be good at one and bad at the other.

Don't confuse

Checkpoint (Spark's saved progress for a stream) vs a Delta table version (a snapshot of the table, lesson 00-10). Both mark "where we were", for different things.

Check yourself

Quiz

1. A dashboard must update within seconds of each event. Which approach fits?

Seconds of latency need a stream that keeps running. Scheduled runs, even incremental ones, leave data stale between runs.

2. What does trigger(availableNow=True) do?

It drains the backlog (possibly in several micro-batches) and stops, which makes it ideal for scheduled incremental jobs.

3. What lets a stream continue where it left off after a restart?

The checkpoint records which data has been processed. Without it, Spark cannot know where it stopped.

4. A scheduled job takes longer every month because it re-reads all history. What's the best fix?

Incremental processing reads only new data, so run time tracks the amount of new data, not total history.

Wrap-up

Key takeaways

  • Batch processes chunks on a schedule; streaming processes new events continuously in micro-batches.
  • The trade-off is latency (freshness) vs compute cost.
  • A checkpoint remembers progress, so streams restart safely and process only new data.
  • availableNow = streaming bookkeeping with batch-style scheduling; it replaced Trigger.Once.
