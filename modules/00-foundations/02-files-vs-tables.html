Files vs tables

Data starts life as files in folders. People want tables. This lesson shows what a table adds on top of files, and why that matters the day a file arrives broken.

The idea

The idea in plain English

A file is a named chunk of bytes saved somewhere, like rides_monday.csv. Files sit in folders (also called directories). A computer can store any file, but it does not know what is inside it.

A table is data you can ask questions about by name, such as "sum the price column of the rides table". A table has rows (one per thing, like one ride) and columns (one per fact, like price).

The key word is schema: the list of a table's columns and the type of each one (price is a decimal number, started_at is a timestamp). Data about data, like the schema, is called metadata.

On Databricks, a table's rows still live in files underneath. What makes it a table is the extra layer on top: a name, a schema, and rules. One important rule is schema enforcement: the table refuses writes whose columns or types do not fit its schema. That stops one bad file from quietly spoiling everything.

A folder of files is a shoebox of paper receipts. Everything is in there, but every shop prints receipts differently, and adding them up means reading each one by hand. A table is a ledger with printed column headings. Anyone can total a column in seconds, and the bookkeeper refuses entries that do not fit the columns.

Code

In code

Reading files directly: you must say where they are and how to read them, every single time.

# Files: point at a folder path and describe the format yourself
monday = (spark.read
          .option("header", True)
          .csv("/Volumes/bike_shop/raw/landing/rides/rides_monday.csv"))
monday.printSchema()   # Spark guessed the columns: every CSV value starts as text

Creating a table: the schema is written down once, and everyone uses the name afterwards.

-- A table: a name plus a schema. Its files are managed for you.
CREATE TABLE IF NOT EXISTS bike_shop.bronze.rides (
  ride_id  STRING,
  price    DECIMAL(8,2)
);

-- Anyone can now query by name. No paths, no format options.
SELECT SUM(price) FROM bike_shop.bronze.rides;

-- See the files and metadata behind the table
DESCRIBE DETAIL bike_shop.bronze.rides;
# Appending a file whose columns don't fit fails, by design
wednesday = spark.read.option("header", True).csv(".../rides_wednesday.csv")
wednesday.write.mode("append").saveAsTable("bike_shop.bronze.rides")
# -> error: the column 'cost' is not in the table's schema

# Opting in to schema evolution adds the new column instead (use with care)
(wednesday.write.mode("append")
   .option("mergeSchema", "true")
   .saveAsTable("bike_shop.bronze.rides"))

Options

What if I change this?

ChangeEffect
Query raw files instead of a tableWorks for a quick look. But every reader must repeat the path and format options, and nothing stops odd files from changing the answer.
Schema enforcement (the default for Delta tables)Writes with unknown columns, or values that can't be safely converted, fail with an error. Bad data stays out; someone must fix the input.
Add mergeSchema on a writeNew columns in the data are added to the table instead of failing. Handy for real change, risky for typos: a misspelled column becomes a permanent new one.
Incoming data is missing a nullable columnThe write succeeds and that column is NULL (empty) for the new rows.
Incoming data is missing a NOT NULL columnThe write fails, because the table promised that column always has a value.
Let Spark guess types from CSV (schema inference)Quick, but guesses can be wrong or change from file to file. For production, declare the schema.

Two ways to look at the same data

Schema-on-read

Store anything; decide its shape when you read it. Flexible for raw landing zones. Every reader can get a different answer.

Schema-on-write

Decide the shape first; only matching data gets in. Reliable for tables people trust. Needs a plan for when the source changes.

Exam traps

Exam traps and look-alikes

Trap

"The table rejected my write, so the table is broken." No: rejection is schema enforcement doing its job. The fix is to change the data or opt in to schema evolution, not to drop the table.

Trap

A table is not a copy of data "somewhere else". Its rows are files in storage; the table is the metadata that names, describes and guards them.

Don't confuse

Schema enforcement = reject data that doesn't fit. Schema evolution = change the table's schema to fit new data. One protects, the other adapts.

Don't confuse

Schema (the list of columns and types) vs a Unity Catalog schema (a container that holds tables, lesson 00-11). Same word, two meanings.

Check yourself

Quiz

1. What does a table add on top of plain files?

The rows still live in files. The table is the metadata layer: what it is called, which columns it has, and which writes it accepts.

2. A file arrives with an extra column the table doesn't have. Enforcement is on and no schema evolution is set. What happens?

Columns being written must exist in the table. Adding them needs an explicit opt-in such as mergeSchema.

3. The new data is missing a column that the table allows to be empty. What happens?

A missing nullable column simply gets NULL. Only a missing NOT NULL column makes the write fail.

4. Which phrase describes reading a folder of CSV files and working out the columns at read time?

Schema-on-read decides the shape when reading. Tables use schema-on-write: shape first, then only matching data gets in.

Wrap-up

Key takeaways

  • Files hold bytes; tables add a name, a schema and rules on top of those files.
  • People query tables by name, not by path, so everyone gets the same answer.
  • Schema enforcement rejects writes that don't fit. Schema evolution is a deliberate opt-in.
  • Missing nullable columns become NULL; unknown columns or unsafe types fail the write.
