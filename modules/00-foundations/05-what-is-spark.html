What is Apache Spark?

The idea

The idea in plain English

Apache Spark is open-source software for processing large amounts of data across many computers at once. One computer would take hours to read a billion rows; ten computers working together can take minutes.

A group of computers working together is a cluster. In a Spark cluster:

  • The driver is the boss. It reads your code, plans the work, and hands out pieces.
  • Executors are the workers. They do the actual reading and calculating. On Databricks, each worker machine runs one executor.

Spark splits data into partitions: chunks of rows that can be processed independently. Each piece of work on one partition is a task. An executor has several cores (processors), and each core runs one task at a time.

Two more ideas matter a lot. First, Spark is lazy: steps like "filter" or "join" (transformations) only add to a plan. Nothing runs until you ask for a result, such as "count", "show" or "write" (an action). Waiting lets Spark optimise the whole plan at once.

Second, some steps need rows with the same key on the same machine, such as "total per bike". Moving rows between executors to arrange that is a shuffle. Shuffles send data over the network, so they are often the slowest part of a job.

Picture a restaurant kitchen at dinner rush. The head chef (driver) reads the orders and plans them. Line cooks (executors) each have a few burners (cores). Every dish is split into small jobs (tasks) on portions of ingredients (partitions). The head chef doesn't start anyone cooking until an order is actually placed (an action). And if every cook must pass ingredients to one particular cook to finish a sauce, that hand-off (shuffle) slows the whole kitchen.

Code

In code

On Databricks, a Spark session called spark is ready in every notebook. You never have to create it.

from pyspark.sql import functions as F

rides = spark.read.table("bike_shop.silver.rides")       # transformation: nothing is read yet
paid  = rides.filter(F.col("price") > 0)                 # transformation: plan grows
per_bike = paid.groupBy("bike_id").agg(F.sum("price").alias("revenue"))  # still nothing; will need a shuffle

per_bike.explain()     # prints the plan Spark made. Still no data processed.

per_bike.count()       # ACTION: now Spark runs the whole plan as a job
display(per_bike)      # ACTION (Databricks notebooks): runs it again to show results

# How many partitions does the data have right now?
rides.rdd.getNumPartitions()   # works on classic compute; serverless may not allow .rdd

Each action runs the plan again from the start. Calling several actions on the same DataFrame repeats the work. Later lessons show when caching helps and when it hurts.

Options

What if I change this?

ChangeEffect
Add more executors (or cores)More tasks run at once, so jobs with many partitions finish faster. Once there are more cores than tasks, extra cores sit idle.
Too few partitions (e.g. 2 for a huge table)Only 2 tasks can run, so most cores wait. Each task is huge and may run out of memory.
Far too many tiny partitionsEach task does almost nothing; time is spent on scheduling overhead instead of work.
Add a groupBy or joinOften adds a shuffle: rows move across the network, and the job gains a new stage.
Add more transformationsNothing runs yet. Spark just extends the plan and optimises it when an action comes.
Call several actions on one DataFrameThe plan runs once per action, repeating the work each time.

The work hierarchy

1 per action

Job

All the work Spark does to answer one action. (A Spark job is not a Lakeflow job.)

split at shuffles

Stage

A run of steps that need no data movement. Each shuffle starts a new stage.

1 per partition

Task

One stage's work on one partition, run by one core.

In real life

Real-life scenarios

ScenarioWhat happensFix
A cluster has 64 cores but a job uses only 4The data has only 4 partitions, so only 4 tasks exist.Split the data into more partitions, or check why the input is so few files.
One task runs 20 minutes while the others take 10 secondsOne key (say, one very busy bike) has far more rows: data skew.Spot it in the Spark UI (module 08); handle skewed keys (module 05).
collect() on a billion-row DataFrame crashes the notebookEvery row is pulled back to the driver, which runs out of memory.Aggregate or limit first; write large results to a table instead.
A notebook calls count() after every step "to check"Each count re-runs the plan, multiplying the cost.Remove debugging actions from production code.

Exam traps

Exam traps and look-alikes

Trap

"The filter ran when I executed that cell." No: a transformation only builds the plan. The work happens at the first action.

Trap

Adding nodes doesn't speed up a job that has fewer partitions than cores. Parallelism is limited by the number of tasks.

Don't confuse

Driver (plans, coordinates, holds notebook state) vs executor (processes partitions). Out-of-memory on the driver often means something was collected to it.

Don't confuse

Spark job (work for one action, seen in the Spark UI) vs Lakeflow job (a scheduled workflow of tasks, module 01). Same word, different things.

Check yourself

Quiz

1. You run df2 = df.filter(...). What does Spark do?

filter is a transformation. Spark records it and waits for an action before running anything.

2. Which of these is an action?

count() needs a real answer, so it triggers a job. The others only extend the plan.

3. Data has 8 partitions. The cluster has 32 cores. How many tasks run at once in a simple stage?

One task per partition, so only 8 tasks exist. The other 24 cores sit idle.

4. Why is a shuffle usually expensive?

Grouping or joining needs matching keys together, so rows travel between machines. Network and disk work make it slow.

Wrap-up

Key takeaways

  • Spark splits data into partitions and runs one task per partition on executor cores, in parallel.
  • The driver plans and coordinates; executors do the work.
  • Transformations are lazy; actions run the plan as a job.
  • Shuffles move data between executors and split a job into stages; they are often the slow part.
