The idea

The idea in plain English

Databricks is a cloud platform for data engineering, analytics and AI. It runs on AWS, Azure or Google Cloud. You open it in a web browser; it runs Spark for you, stores data in your cloud storage, and governs who can see what.

The idea of keeping all data in cheap object storage, in open table formats, and running both data engineering and analytics on it is called a lakehouse: a data lake's low cost with a data warehouse's reliability.

Databricks splits into two halves:

  • The control plane: the web app and back-end services, run by Databricks. It stores your notebooks, jobs and settings.
  • The compute plane: where data is actually processed. Serverless compute runs in Databricks' cloud account; classic compute runs in your own cloud account. Either way, your data stays in your storage.

A workspace is your team's space in the web app: folders of notebooks and files, jobs, pipelines, dashboards, and the data catalog.

A notebook is a web document made of cells. Each cell holds code (Python, SQL, Scala or R) or text. You run cells one at a time and see results under each. Variables made in one cell stay in memory for later cells: that memory is the notebook's state, and it lives on the attached compute.

Think of a shared office kitchen run by a catering company. The company's head office (control plane) keeps the recipes, rotas and rules. The actual cooking happens on stoves (compute plane), either the caterer's own (serverless) or ones installed in your building (classic). Your ingredients never leave your pantry (your cloud storage).

Code

In code

A notebook has a default language. A magic command at the top of a cell (starting with %) switches that one cell:

# Cell 1 (Python, the notebook's default language)
rides = spark.read.table("bike_shop.silver.rides")
rides.createOrReplaceTempView("rides_v")   # lets SQL cells see it

# Cell 2
# %sql
# SELECT town, COUNT(*) AS rides FROM rides_v GROUP BY town

# Cell 3: install a library for this notebook only
# %pip install great-tables

# Cell 4: run another notebook here, sharing its variables
# %run ./shared/helpers

# Cell 5: a text cell for notes
# %md
# ## Ride counts by town

Notebooks are also files you can version in Git. A Python notebook saved as source looks like this:

# Databricks notebook source
rides = spark.read.table("bike_shop.silver.rides")

# COMMAND ----------

display(rides.groupBy("town").count())

Options

What if I change this?

ChangeEffect
Run cells out of orderA cell may use a variable that doesn't exist yet, or an old value. "Run all" from the top is the honest test.
Detach compute, or let it shut downAll in-memory state (variables, temp views, %pip installs) is lost. Code and saved tables remain.
%pip install in a notebookThe library is available to this notebook's session only. Module 01 covers proper dependency management.
%run ./other_notebookRuns that notebook inside this one, so its functions and variables become available here.
Serverless instead of classic computeNo machines to manage and fast start-up; compute runs in Databricks' account. Some low-level features differ (lesson 00-09).

Exam traps

Exam traps and look-alikes

Trap

"Databricks stores my table data in the control plane." No: table data lives in cloud storage. The control plane holds code, settings and metadata services.

Trap

Notebook state is not saved. Variables, temp views and %pip installs disappear when compute detaches or restarts.

Don't confuse

Workspace (a team's environment in the web app) vs account (the top level that can hold many workspaces and shared settings).

Don't confuse

%run (runs another notebook inline, sharing variables) vs running a notebook as a job task (separate run, separate state).

Check yourself

Quiz

1. Where does the data in your Databricks tables live?

Tables are files in cloud storage. The control plane runs the web app and services; compute reads and writes the storage.

2. Your compute restarts. What is lost?

Notebook state lives in memory on compute. Code is stored in the workspace and tables in storage, so both survive.

3. In a Python notebook, how do you run one cell as SQL?

Magic commands like %sql, %md and %pip change what one cell does. (Calling spark.sql("…") in Python also works.)

4. Serverless compute runs where?

Serverless compute is managed by Databricks in its own account. Classic compute runs in your cloud account.

Wrap-up

Key takeaways

  • Databricks = Spark + storage + governance as one web platform: a lakehouse.
  • The control plane holds the app and your code; the compute plane processes data; data stays in your storage.
  • Notebooks run cells in Python, SQL, Scala or R; magic commands switch a cell's behaviour.
  • Notebook state is in memory and vanishes when compute detaches. Save results in tables.
