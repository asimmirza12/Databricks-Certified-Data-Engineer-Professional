Delta Lake basics

Delta Lake is why a pile of files in object storage can behave like a trustworthy database table. One idea does most of the work: a log of every change.

The idea

The idea in plain English

A Delta table is a folder holding Parquet data files plus a subfolder called _delta_log. That subfolder is the transaction log: an ordered list of numbered files, one per change. Each change is a commit, and each commit creates a new version of the table (0, 1, 2…).

A commit says things like "add file A, remove file B". Data files are never edited (object storage can't, lesson 00-07). To change rows, Delta writes new files and records that old ones are no longer part of the table. Readers look at the log to know which files make up the current version.

This gives ACID guarantees, the promises databases make:

  • Atomic: a write fully happens or not at all. A crash halfway leaves no half-written data.
  • Consistent: the table always follows its rules, like its schema.
  • Isolated: readers see a complete version, never someone's half-finished write.
  • Durable: once committed, it stays committed.

Because old versions stay in the log, you can query the past: time travel. You can also roll back with RESTORE. Old files pile up, so VACUUM deletes files that are no longer needed and are older than a retention period (7 days by default).

A Delta table is like a bank account. The money (data files) sits in the vault. The statement (transaction log) lists every deposit and withdrawal in order. Your balance is worked out from the statement. You can ask "what was my balance last Tuesday?" by reading the statement up to that line. Nobody erases a line; mistakes are fixed by adding a new one.

Code

In code

-- Every statement below is one commit = one new version
CREATE TABLE bike_shop.silver.rides (ride_id STRING, town STRING, price DECIMAL(8,2));
INSERT INTO bike_shop.silver.rides VALUES ('r01', 'Northport', 6.00), ('r02', 'Riverside', 11.50);
UPDATE bike_shop.silver.rides SET price = 9.50 WHERE ride_id = 'r02';
DELETE FROM bike_shop.silver.rides WHERE ride_id = 'r01';

-- See the log: version, time, operation, who did it
DESCRIBE HISTORY bike_shop.silver.rides;

-- Time travel: read an older version
SELECT * FROM bike_shop.silver.rides VERSION AS OF 1;
SELECT * FROM bike_shop.silver.rides TIMESTAMP AS OF '2026-11-18 09:00:00';

-- Undo: make an old version current again (this is itself a new commit)
RESTORE TABLE bike_shop.silver.rides TO VERSION AS OF 1;

-- Delete files no longer in the table and older than the retention period (default 7 days)
VACUUM bike_shop.silver.rides;
# The same time travel from Python
v1 = spark.read.option("versionAsOf", 1).table("bike_shop.silver.rides")

On Unity Catalog managed tables, predictive optimization can run maintenance like VACUUM and OPTIMIZE for you (module 05).

Options

What if I change this?

ChangeEffect
delta.deletedFileRetentionDuration (default 7 days)How long removed files are kept before VACUUM may delete them. Longer = more time travel, more storage cost.
delta.logRetentionDuration (default 30 days)How long history entries are kept. Time travel needs both the log entry and the data files, so in practice the 7-day file retention is the usual limit.
Run VACUUMOld unneeded files are deleted. Time travel to versions that needed them stops working. Storage cost drops.
Vacuum with a retention below 7 daysNot recommended: running queries or streams may still need those files and can fail.
RESTORE to an older versionAdds a new commit that makes the old state current. History is kept, so you can restore forward again.
Many small insertsMany small files. OPTIMIZE compacts them into bigger ones (module 05).

Exam traps

Exam traps and look-alikes

Trap

"DELETE removes the data from storage." Not yet: the rows are gone from the current version, but old files remain until VACUUM, and time travel can still read them.

Trap

"Log retention is 30 days, so I can time travel 30 days back." Usually not: data files are vacuumed after 7 days by default. Both settings matter.

Don't confuse

RESTORE (changes the table, creates a new version) vs VERSION AS OF (only reads the past).

Don't confuse

VACUUM (deletes unneeded old files) vs OPTIMIZE (rewrites small files into bigger ones). One cleans up, one tidies up.

Check yourself

Quiz

1. What does an UPDATE do to the data files of a Delta table?

Files are never edited. A new file holds the changed rows; the commit marks the old file as removed. (Deletion vectors, module 05, can avoid rewriting the whole file.)

2. A job crashes halfway through writing to a Delta table. What do readers see?

Without a commit in the log, the new files aren't part of any version. That is atomicity.

3. After VACUUM with default settings, which time travel can fail?

VACUUM deletes files that left the table more than the retention period ago (7 days by default). Versions that needed them can't be read.

4. What does RESTORE TABLE t TO VERSION AS OF 5 do?

RESTORE writes a new version. History is kept, so the later versions remain visible in DESCRIBE HISTORY.

Wrap-up

Key takeaways

  • A Delta table = Parquet files + _delta_log, a list of commits; each commit is a version.
  • Files are never edited: changes add new files and mark old ones removed. This gives ACID writes.
  • Time travel reads old versions; RESTORE makes one current again as a new commit.
  • VACUUM deletes old files past retention (7 days default), which limits time travel.
