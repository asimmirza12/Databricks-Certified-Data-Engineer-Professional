The idea

The idea in plain English

Lakeflow pipelines (formerly Delta Live Tables, then Lakeflow Declarative Pipelines) are Databricks' declarative way to build data pipelines. They are built on the open-source Apache Spark Declarative Pipelines project, with extra Databricks features (such as the AUTO CDC APIs).

You write source files (SQL or Python) that each declare a dataset:

  • A streaming table: a table fed incrementally; each new input row is processed once. Typical for bronze and silver.
  • A materialized view: a table holding the up-to-date result of a query, recomputed (incrementally when possible) on each update. Typical for gold aggregates.
  • A temporary view: a named step inside the pipeline that stores nothing and isn't published.

The pipeline reads all the declarations, works out which dataset depends on which, and draws a dependency graph (often called a DAG: directed acyclic graph). Running the pipeline is called an update: it refreshes datasets in the right order, manages checkpoints and compute, retries failures, and writes an event log.

A pipeline runs in triggered mode (refresh what's new, then stop: usually scheduled by a job) or continuous mode (keep running and process data as it arrives).

In Python, the module is pyspark.pipelines, imported as dp. The old dlt module still works, but the new name is recommended.

Ordering a house versus building it brick by brick. You give the architect a plan: kitchen here, bedroom above it, roof on top (declarations). The builder works out that foundations come before walls, hires the crew, redoes a wall if it cracks, and keeps a site diary. You change the plan; they work out what to rebuild.

Code

In code

The same pipeline in SQL. STREAM(...) marks an incremental read:

-- bronze: streaming table fed by Auto Loader (lesson 01-09)
CREATE OR REFRESH STREAMING TABLE rides_bronze
AS SELECT *, _metadata.file_path AS source_file
FROM STREAM read_files('/Volumes/bike_shop/raw/landing/rides/', format => 'json');

-- silver: streaming table reading bronze incrementally
CREATE OR REFRESH STREAMING TABLE rides_silver
AS SELECT ride_id, town, CAST(price AS DECIMAL(8,2)) AS price, CAST(started_at AS TIMESTAMP) AS started_at
FROM STREAM(rides_bronze)
WHERE price IS NOT NULL;

-- gold: materialized view, always reflects the current silver data
CREATE OR REFRESH MATERIALIZED VIEW revenue_by_town
AS SELECT town, DATE(started_at) AS ride_date, SUM(price) AS revenue
FROM rides_silver
GROUP BY ALL;

And in Python, with pyspark.pipelines:

from pyspark import pipelines as dp
from pyspark.sql import functions as F

@dp.table(comment="Raw rides as they arrived")        # returns a streaming DataFrame → streaming table
def rides_bronze():
    return (spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("/Volumes/bike_shop/raw/landing/rides/"))

@dp.table
def rides_silver():
    return (spark.readStream.table("rides_bronze")        # the pipeline sees this dependency
            .where(F.col("price").isNotNull())
            .withColumn("price", F.col("price").cast("decimal(8,2)")))

@dp.materialized_view
def revenue_by_town():
    return (spark.read.table("rides_silver")                # batch read → recomputed result
            .groupBy("town", F.to_date("started_at").alias("ride_date"))
            .agg(F.sum("price").alias("revenue")))

Notice what's missing: no writeStream, no checkpoint paths, no saveAsTable, no ordering. The pipeline publishes each dataset to the pipeline's default catalog and schema.

Options

What if I change this?

ChangeEffect
Triggered modeEach update processes what's new, then compute stops. Schedule it with a job. Cheapest for most workloads.
Continuous modeCompute keeps running and processes data as it arrives. Lowest latency, highest cost.
Full refreshStreaming tables are emptied and rebuilt from all available source data; checkpoints reset. Use with care: sources whose old data is gone (e.g. expired messages) can't be replayed.
Development modeFor iterating: compute is reused between updates and automatic retries are off so errors show fast.
Production modeFailed updates retry automatically (for example after transient cloud errors); compute restarts for recoverable problems.
Serverless pipelineNo compute settings; enables incremental refresh of materialized views and the pipeline environment for dependencies.
Read a table with spark.read instead of readStreamYou get a materialized view (batch, recomputed) rather than incremental streaming processing.

Exam traps

Exam traps and look-alikes

Trap

Old names in questions: Delta Live Tables / DLT and Lakeflow Declarative Pipelines are the same product as Lakeflow pipelines. APPLY CHANGES is now AUTO CDC.

Trap

Changing a streaming table's logic does not reprocess old rows. Only a full refresh does.

Don't confuse

Triggered vs continuous (how the pipeline runs) vs development vs production mode (retries and compute reuse).

Don't confuse

Temporary view (pipeline-only, stores nothing) vs materialized view (stored, published, kept current).

Check yourself

Quiz

1. How does a pipeline know to update bronze before silver?

Each declaration references its inputs, so the pipeline derives the graph and the order.

2. A gold table must show correct totals even when silver rows are corrected or deleted. Which dataset type?

Materialized views reflect the current state of their inputs, including updates and deletes. Streaming tables process each new row once.

3. You need fresh data once a day at the lowest cost. Which setup?

Triggered updates process new data and stop, so you pay only while they run.

4. What is the recommended Python module for new pipeline code?

dlt still works, but pyspark.pipelines is the current name.

Wrap-up

Key takeaways

  • Declare streaming tables, materialized views and temporary views; the pipeline builds the graph and runs it.
  • Checkpoints, order, retries and compute are managed for you.
  • Triggered = process and stop; continuous = always on. Production mode retries; development mode doesn't.
  • Logic changes apply to new data only, unless you full refresh.
