Structured Streaming vs Spark Declarative Pipelines

You now know both ways to build streaming ETL. This lesson is about choosing: which constraints point to writing the stream yourself, and which point to declaring a pipeline.

The idea

The idea in plain English

Both options run on the same Structured Streaming engine. The difference is who manages the surrounding work.

  • Structured Streaming (imperative): you write each readStream and writeStream, choose checkpoint paths, triggers and output modes, write foreachBatch logic, and orchestrate the order of streams with jobs. Maximum control, maximum responsibility.
  • Spark Declarative Pipelines (declarative), which you run on Databricks as Lakeflow pipelines: you declare datasets; the pipeline manages dependencies, checkpoints, retries, compute, data-quality expectations, CDC via AUTO CDC, lineage and an event log. Less code, less to operate, but you work within its model.

Some features exist only on one side. AUTO CDC and expectations are pipeline features (AUTO CDC is Databricks-only, not in open-source SDP). Fully custom stateful logic with transformWithState, real-time mode for sub-second latency, and complete freedom over sinks and triggers are Structured Streaming territory, though pipelines do offer sinks and foreach_batch_sink (Python only) for many custom-output cases.

The usual default: start with a pipeline for medallion-style ETL; drop down to Structured Streaming when a specific requirement doesn't fit.

A meal kit versus cooking from scratch. The kit (pipeline) arrives with portions, steps and timings worked out; you just assemble, and it's hard to burn. Cooking from scratch (Structured Streaming) lets you make any dish and tweak every detail, but you shop, time and clean up yourself. Most weeknights the kit wins; the special dinner needs scratch cooking.

Code

In code

The same bronze → silver stream, both ways. Structured Streaming:

# You choose paths, trigger and output, and schedule it with a job
(spark.readStream.table("bike_shop.bronze.rides_raw")
    .where("price IS NOT NULL")
    .writeStream
    .option("checkpointLocation", "/Volumes/bike_shop/silver/_checkpoints/rides")
    .trigger(availableNow=True)
    .toTable("bike_shop.silver.rides"))

Lakeflow pipeline, with a data-quality rule thrown in:

from pyspark import pipelines as dp

@dp.table(name="rides")
@dp.expect_or_drop("has_price", "price IS NOT NULL")   # module 03; dropped rows counted in the event log
def rides():
    return spark.readStream.table("bike_shop.bronze.rides_raw")
# no checkpoint, trigger or write code: the pipeline handles them

A custom sink inside a pipeline (for cases that once forced plain Structured Streaming):

@dp.foreach_batch_sink(name="ops_db_sink")               # Python only; check preview status in the docs
def to_ops_db(df, batch_id):
    df.write.format("jdbc").option("dbtable", "bike_alerts").mode("append").save()  # connection options omitted

@dp.append_flow(target="ops_db_sink")
def alerts_to_ops():
    return spark.readStream.table("rides").where("minutes > 180")

Options

What if I change this?

RequirementPushes towards
Data-quality rules with metrics (warn / drop / fail)Pipeline: expectations are built in.
CDC with SCD Type 1 or 2Pipeline: AUTO CDC. (Hand-written: MERGE in foreachBatch.)
Small team, many streams, little time to operate themPipeline: managed checkpoints, ordering, retries, monitoring.
Sub-second latency (real-time mode)Structured Streaming.
Custom per-key state with timers (transformWithState)Structured Streaming.
Unusual sink or fine control of triggers per streamStructured Streaming, or pipeline sinks / foreach_batch_sink if they fit.
Logic written in SQL by analystsPipeline: SQL is a first-class pipeline language.
Large existing, working Structured Streaming code baseOften keep it; migrate where pipeline features pay off.

Exam traps

Exam traps and look-alikes

Trap

"Pipelines can't do streaming." They are streaming: streaming tables run on Structured Streaming underneath.

Trap

AUTO CDC is a Databricks Lakeflow pipelines feature, not part of open-source Apache Spark Declarative Pipelines.

Don't confuse

Apache Spark Declarative Pipelines (the open-source framework) vs Lakeflow pipelines (Databricks' product built on it, with extra features).

Don't confuse

Pipeline continuous mode (always-on micro-batches, seconds) vs Structured Streaming real-time mode (sub-second, strict requirements).

Check yourself

Quiz

1. A small team needs bronze/silver/gold streaming ETL with data-quality metrics and minimal operations work. Best fit?

Pipelines manage checkpoints, ordering, retries and expectations, which is exactly what a small team wants.

2. Which requirement points most strongly to plain Structured Streaming?

Real-time mode is a Structured Streaming feature. The others are pipeline strengths.

3. In a pipeline, who manages streaming checkpoints?

Checkpoints are managed for each streaming table and flow.

4. Which statement about AUTO CDC is true?

AUTO CDC is a Lakeflow pipelines feature that isn't in the open-source framework.

Wrap-up

Key takeaways

  • Same engine; the difference is how much the platform manages for you.
  • Pipelines: managed checkpoints, ordering, retries, expectations, AUTO CDC, event log. Default for medallion ETL.
  • Structured Streaming: real-time mode, transformWithState, full control of sinks and triggers.
  • Pipeline sinks and foreach_batch_sink close part of the custom-output gap.
