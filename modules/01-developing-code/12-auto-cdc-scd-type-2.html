AUTO CDC and SCD Type 2

Sometimes "what is it now?" isn't enough: you need "what was it on the day of that sale?". SCD Type 2 keeps every version of a row, each with the time range it was true.

The idea

The idea in plain English

With SCD Type 2, an update doesn't overwrite. Instead, the current row is "closed" and a new row is added with the new values. Each row carries two extra columns that AUTO CDC fills in for you:

  • __START_AT: the sequence value (usually a timestamp) from which this version was true.
  • __END_AT: when it stopped being true. NULL means "still current".

So the current row for a key is the one where __END_AT IS NULL, and the row that was true at any moment is the one whose range covers that moment. The values in both columns come from your sequence_by column, which is why they must have the same type.

Not every change deserves a history row. A customer's last_login changes constantly, but you only care when their city or email changes. track_history_column_list (or track_history_except_column_list) says which columns create a new version; changes to other columns just update the current row in place. By default, all columns are tracked.

A delete in Type 2 closes the current row (sets its __END_AT) instead of erasing history.

A passport's stamped pages versus a whiteboard. Type 1 is the whiteboard: wipe and rewrite, the past is gone. Type 2 is the passport: every visa has a "valid from" and "valid until" date, old ones stay in the book, and only one is valid today. And you don't get a new visa every time you change hotels: only changes that matter (tracked columns) get a new stamp.

Code

In code

Python, in a pipeline:

from pyspark import pipelines as dp
from pyspark.sql import functions as F

dp.create_streaming_table("customers_history")

dp.create_auto_cdc_flow(
    target="customers_history",
    source="customers_cdc_bronze",
    keys=["customer_id"],
    sequence_by=F.col("event_ts"),                    # becomes __START_AT / __END_AT
    apply_as_deletes=F.expr("op = 'DELETE'"),       # closes the current version
    except_column_list=["op", "event_ts"],
    stored_as_scd_type=2,                              # keep history
    track_history_column_list=["city", "email"]      # other columns update in place
)

SQL:

CREATE OR REFRESH STREAMING TABLE customers_history;

CREATE FLOW customers_history_flow AS AUTO CDC INTO customers_history
FROM STREAM(customers_cdc_bronze)
KEYS (customer_id)
APPLY AS DELETE WHEN op = 'DELETE'
SEQUENCE BY event_ts
COLUMNS * EXCEPT (op, event_ts)
STORED AS SCD TYPE 2
TRACK HISTORY ON (city, email);

Querying the history:

-- Current version of every customer
SELECT * FROM customers_history WHERE __END_AT IS NULL;

-- Which city each customer lived in when each ride happened
SELECT r.ride_id, r.started_at, c.city
FROM rides_silver r
JOIN customers_history c
  ON r.customer_id = c.customer_id
 AND r.started_at >= c.__START_AT
 AND (r.started_at < c.__END_AT OR c.__END_AT IS NULL);

Options

What if I change this?

ChangeEffect
stored_as_scd_type=2Each tracked change closes the current row and adds a new one with __START_AT/__END_AT.
No track-history list (default)Every column change creates a version. Frequently changing columns can bloat the table.
track_history_column_list=[...] / TRACK HISTORY ON (...)Only these columns create versions; others overwrite the current row.
track_history_except_column_listTrack every column except the listed ones.
A delete event (with apply_as_deletes)The current version gets an __END_AT; history is kept. No row remains current.
Declare the target schema yourselfYou must include __START_AT and __END_AT with the same type as the sequence_by column.
Late, out-of-order eventAUTO CDC slots it into the right place in history based on sequence_by, adjusting neighbouring versions.

Exam traps

Exam traps and look-alikes

Trap

The current row is the one with __END_AT IS NULL, not the one with the largest __START_AT after a delete (a deleted key has no current row).

Trap

Untracked columns still change: they're updated in place on the current row, just without creating a new version.

Don't confuse

SCD Type 2 history (business history, kept forever, queryable by range) vs Delta time travel (technical table versions, limited by VACUUM retention).

Don't confuse

track_history_column_list (which columns create versions) vs except_column_list (which columns are stored at all).

Check yourself

Quiz

1. How do you select only the current version of each customer from an SCD Type 2 table built by AUTO CDC?

An open-ended range (no end) marks the version that is true now.

2. Only changes to city should create new versions; last_login changes should just update the current row. Which setting?

Track-history settings choose which columns create versions. except_column_list would drop last_login entirely.

3. What does a delete event do in SCD Type 2?

History is preserved; the key simply has no current version after the delete.

4. Where do __START_AT and __END_AT values come from?

They're taken from sequence_by, which is why a declared schema must give them the same type.

Wrap-up

Key takeaways

  • stored_as_scd_type=2 keeps every version with __START_AT/__END_AT taken from sequence_by.
  • Current rows: __END_AT IS NULL. Point-in-time: join on the validity range.
  • Track history only on columns that matter; others update in place.
  • Deletes close the current version; history stays.
