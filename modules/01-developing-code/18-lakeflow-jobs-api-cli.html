The idea

The idea in plain English

An API (application programming interface) is a way for programs to talk to a service. Databricks has a REST API: you send HTTPS requests to URLs like https://<workspace>/api/2.2/jobs/run-now with a JSON body, and get JSON back. The Jobs API is currently version 2.2.

Three tools wrap the same API:

  • REST calls directly (e.g. with curl, or any language's HTTP library).
  • The Databricks CLI: commands like databricks jobs run-now 123. Most CLI commands map one-to-one to an API call.
  • The Databricks SDK for Python: WorkspaceClient().jobs.run_now(...), with typed objects and helpers that wait for runs to finish.

Every call needs authentication: proof of who's calling. People usually log in with OAuth (databricks auth login). Automation should use a service principal with OAuth machine-to-machine credentials rather than a person's token, so pipelines don't break when someone leaves.

Key Jobs API operations: create (returns a job_id), run-now (returns a run_id), runs/get (status of a run), runs/list, runs/cancel, update (change some settings) and reset (replace all settings).

The Jobs UI is talking to a bank teller. The REST API is the bank's phone line with a strict script. The CLI is a speed-dial button that reads the script for you, and the SDK is a banking app. All four reach the same accounts; each asks you to prove who you are first.

In code

Authenticate once. The CLI and SDK read the same profiles:

# A person, interactively (OAuth in the browser; saved as a profile in ~/.databrickscfg)
databricks auth login --host https://dbc-1234.cloud.databricks.com --profile dev

# Automation (e.g. in CI): a service principal's OAuth credentials as environment variables
export DATABRICKS_HOST=https://dbc-1234.cloud.databricks.com
export DATABRICKS_CLIENT_ID=<service-principal-application-id>
export DATABRICKS_CLIENT_SECRET=<from-your-secret-store>

CLI:

databricks jobs create --json @nightly_job.json          # prints {"job_id": 123}
databricks jobs run-now 123                              # waits for the run by default (see --no-wait)
databricks jobs list-runs --job-id 123 --limit 5
databricks jobs get-run 4567                             # state, tasks, timings
databricks jobs cancel-run 4567

Python SDK, e.g. from another system's script:

from databricks.sdk import WorkspaceClient
from databricks.sdk.service import jobs

w = WorkspaceClient()                                  # picks up env vars or a profile

created = w.jobs.create(
    name="nightly_bike_shop",
    tasks=[jobs.Task(
        task_key="ingest",
        notebook_task=jobs.NotebookTask(notebook_path="/Workspace/bike_shop/ingest"),
    )],
    schedule=jobs.CronSchedule(quartz_cron_expression="0 0 2 * * ?", timezone_id="UTC"),
)

run = w.jobs.run_now(job_id=created.job_id, job_parameters={"run_date": "2026-11-19"}).result()  # waits
print(run.state.life_cycle_state, run.state.result_state)

Raw REST, when no SDK is available:

curl -s -X POST "$DATABRICKS_HOST/api/2.2/jobs/run-now" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"job_id": 123, "job_parameters": {"run_date": "2026-11-19"}}'
# → {"run_id": 4567, "number_in_job": 4567}

For jobs that live in a repo, prefer a bundle (databricks bundle deploy / run) over hand-written jobs create calls: the bundle keeps the definition in Git and updates it in place.

Options

What if I change this?

ChangeEffect
jobs update with a few fieldsChanges only those settings; the rest stay.
jobs reset with new settingsReplaces the whole job definition; anything you didn't include is gone.
run-now with job_parametersOverrides parameter defaults for this run only.
jobs submit (one-time run)Runs a workload without saving a job. Handy for tests; nothing appears in the jobs list to re-run.
Use a personal access token in CIWorks, but tied to a person and long-lived. Prefer a service principal with OAuth.
Poll runs/get in a tight loopWasteful and may hit rate limits. Poll every few seconds, or let the SDK's .result() wait.
Hard-code job_id across workspacesIDs differ per workspace. Look jobs up by name, or deploy with bundles.

Run state

life_cycle_state

Where the run is: PENDING, RUNNING, TERMINATING, TERMINATED (also SKIPPED, INTERNAL_ERROR).

Run state

result_state

The outcome once finished: SUCCESS, FAILED, TIMEDOUT, CANCELED.

In real life

Real-life scenarios

ScenarioWhat happensFix
An external scheduler must start the Databricks job after its own stepsIt needs a programmatic trigger.Call run-now and poll runs/get until TERMINATED, then check result_state.
CI deploys break when an engineer leavesCI used that person's token.Use a service principal with OAuth credentials.
A script "updated" a job and wiped its scheduleIt called reset with partial settings.Use update for partial changes, or manage jobs with bundles.
A script checks status and reports success while the run is still goingIt read life_cycle_state = RUNNING as "no error".Wait for TERMINATED, then read result_state.

Exam traps

Exam traps and look-alikes

Trap

run-now returns a run_id, not a result. Success is only known when the run reaches TERMINATED with result_state SUCCESS.

Trap

reset replaces everything; update merges. Picking the wrong one is a classic wrong answer.

Don't confuse

job_id (the saved job) vs run_id (one execution of it).

Don't confuse

jobs run-now (run a saved job) vs jobs submit (one-off run without saving a job).

Check yourself

Quiz

1. A script calls run-now. How does it know whether the run succeeded?

run-now only returns a run ID; the outcome appears in result_state once the run terminates.

2. You want to change only a job's schedule via the API. Which operation?

update changes the given fields; reset would replace the whole definition and drop everything else.

3. What's the recommended identity for a CI system calling the Jobs API?

Service principals aren't tied to a person, and OAuth credentials are short-lived and managed.

4. Which CLI command starts a saved job with ID 123?

jobs run-now triggers a run of an existing job.

Wrap-up

Key takeaways

  • REST (Jobs API 2.2), CLI and Python SDK all drive the same operations: create, run-now, get/list/cancel runs, update, reset.
  • Authenticate people with OAuth login; automation with a service principal.
  • run-now gives a run_id; wait for TERMINATED and read result_state.
  • update merges, reset replaces. For jobs in Git, use bundles.
