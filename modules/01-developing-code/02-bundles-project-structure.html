Structuring a modular Python bundle project

A bundle with one giant notebook works, but it can't be tested, reused or reviewed well. This lesson shows a project layout that splits code into a package, resources into files, and lets CI build and deploy it.

The idea

The idea in plain English

Modular code is split into small parts that each do one job and can be reused. In Python, a file of functions is a module, and a folder of modules you can install is a package.

A well-structured bundle project keeps four kinds of things apart:

  • Configuration: databricks.yml for bundle-wide settings and targets, and one YAML file per job or pipeline under resources/, pulled in with include.
  • Library code: transformation functions in a Python package under src/. No notebook magic, no hard-coded table names: plain functions that take a DataFrame and return a DataFrame.
  • Entry points: thin notebooks, scripts or pipeline source files that read parameters, call the package, and write results.
  • Tests: under tests/, run with a test framework like pytest (lesson 01-22).

The package is described by pyproject.toml and built into a wheel: a single installable .whl file. The bundle's artifacts section builds the wheel during bundle deploy, uploads it, and job tasks install it. The current default-python template uses uv (a fast Python packaging tool) and pyproject.toml for this.

CI/CD (continuous integration and continuous delivery) means every change is tested automatically, and passing changes are deployed automatically. A modular layout is what makes that possible: tests can import the package without a cluster, and the CLI deploys the same project to each target.

Think of a restaurant kitchen. Recipes (library code) live in one shared binder, not scribbled on each plate. Order tickets (entry points) just say "make recipe 12 for table 4". The menu and opening hours (configuration) are posted separately. A taster (tests) checks each recipe change before it reaches customers. Change the binder once, and every dish that uses that recipe improves.

Code

In code

A typical layout (the default-python template is similar; check the current template with databricks bundle init):

bike_shop_etl/
├── databricks.yml              # bundle name, include, artifacts, targets
├── pyproject.toml              # package metadata and dependencies
├── resources/
│   ├── nightly_rides.job.yml   # one file per job or pipeline
│   └── rides.pipeline.yml
├── src/
│   ├── bike_shop_etl/          # the package: plain, testable functions
│   │   ├── __init__.py
│   │   ├── transforms.py
│   │   └── main.py             # entry point for a wheel task
│   └── notebooks/clean_rides.ipynb   # thin entry point
├── tests/
│   └── test_transforms.py
└── .github/workflows/deploy.yml     # CI/CD

databricks.yml pulls the resource files in and builds the wheel:

bundle:
  name: bike_shop_etl

include:
  - resources/*.yml

artifacts:
  bike_shop_wheel:
    type: whl
    build: uv build --wheel     # runs during bundle deploy
    path: .

targets:
  dev:  { mode: development, default: true }
  prod: { mode: production, variables: { catalog: prod } }

resources/nightly_rides.job.yml runs a function from the wheel on serverless:

resources:
  jobs:
    nightly_rides:
      name: nightly_rides
      tasks:
        - task_key: clean
          python_wheel_task:
            package_name: bike_shop_etl
            entry_point: main             # from [project.scripts] in pyproject.toml
            parameters: ["--catalog", "${var.catalog}"]
          environment_key: default        # required for wheel tasks on serverless
      environments:
        - environment_key: default
          spec:
            environment_version: "4"      # pick a current version; check the docs
            dependencies:
              - ../dist/*.whl           # the wheel built by artifacts

The package function is plain PySpark, so tests can call it directly:

# src/bike_shop_etl/transforms.py
from pyspark.sql import DataFrame, functions as F

def clean_prices(df: DataFrame) -> DataFrame:
    """Keep rides with a positive price, typed as a decimal."""
    return (df.withColumn("price", F.col("price").cast("decimal(8,2)"))
              .where(F.col("price") > 0))

Options

What if I change this?

ChangeEffect
include: [resources/*.yml]Each job or pipeline lives in its own file. Smaller diffs, fewer merge conflicts.
artifacts with type: whlThe wheel is built and uploaded on every deploy, so the job always runs the code from this commit.
No build command givenThe default is a legacy setup.py bdist_wheel build; set uv build --wheel (or similar) for pyproject.toml projects.
Logic written inside notebooks instead of the packageHard to unit-test and reuse; every notebook copies the same code.
Hard-coded table namesThe same code can't run against dev and prod. Pass the catalog as a parameter from a bundle variable.
Bump the version in pyproject.tomlThe wheel file name changes, which makes it clear which build a job ran.

In real life

Real-life scenarios

ScenarioWhat happensFix
A cleaning bug is fixed in one notebook but four others copied the same codeFour jobs keep the bug.Move the function into the package; all jobs import it.
A job runs an old wheel after deployThe wheel path was fixed to an old file name, or the version wasn't bumped and a cached copy was used.Reference the artifact the bundle builds (../dist/*.whl) and bump versions.
Merge conflicts in a 600-line databricks.ymlEvery team edits one file.Split resources into resources/*.yml with include.

Exam traps

Exam traps and look-alikes

Trap

Uploading a wheel by hand and pointing jobs at it defeats the bundle. Let artifacts build and upload it on deploy so code and jobs always match.

Trap

On serverless, wheel and Python script tasks need an environment_key pointing to an environment with the dependencies. Classic-style libraries on the task isn't how serverless gets them.

Don't confuse

pyproject.toml (describes the Python package) vs databricks.yml (describes the bundle and its resources).

Don't confuse

include (more YAML config files) vs artifacts (things to build, like a wheel) vs sync (which files are uploaded).

Check yourself

Quiz

1. Your databricks.yml is huge and causes merge conflicts. What's the bundle-native fix?

include merges extra YAML files into the bundle, so each job or pipeline can live in its own file.

2. How should a bundle get a freshly built wheel of your package to a job?

The artifact is built during deploy and referenced from the job, so jobs always run the code from that commit.

3. Why keep transformations as plain functions in a package?

Spark speed is the same. The gain is testability and reuse; notebooks become thin entry points.

4. A python_wheel_task runs on serverless. What must the task reference?

Serverless tasks get dependencies from job environments; wheel and script tasks require environment_key.

Wrap-up

Key takeaways

  • Split config (databricks.yml + resources/*.yml), library code (src/ package), entry points and tests.
  • Build the package as a wheel with artifacts during deploy; reference it from tasks.
  • On serverless, tasks get dependencies through job environments and environment_key.
  • CI order: test → validate → build → deploy, per target.
