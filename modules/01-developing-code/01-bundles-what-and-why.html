Declarative Automation Bundles: what and why

Clicking jobs together in the UI works once. For a team shipping changes every week, you want jobs, pipelines and code described in files, reviewed in Git and deployed the same way every time. That is what bundles do.

The idea

The idea in plain English

Declarative Automation Bundles (formerly Databricks Asset Bundles, or DABs) let you describe Databricks resources in text files that live next to your code. A resource is something the platform runs or hosts: a Lakeflow job, a Lakeflow pipeline, a dashboard, a model serving endpoint, and more.

"Declarative" means you write what should exist ("a job called nightly_rides that runs this notebook at 02:00"), not the clicks to create it. The tool works out what to create, change or delete. This idea is called infrastructure as code.

The main file is databricks.yml, written in YAML (a plain-text format of indented key: value lines). A bundle has three main parts:

  • bundle: its name.
  • resources: the jobs, pipelines and other things to create.
  • targets: the places you deploy to, such as dev and prod, each with its own workspace and settings.

You drive bundles with the Databricks CLI (command-line tool): databricks bundle validate checks the files, deploy uploads code and creates or updates resources, run starts a job or pipeline, and destroy removes what the bundle deployed. The command is still databricks bundle after the rename.

A bundle is a recipe card versus cooking from memory. From memory, each cook makes the dish a bit differently and nobody can say what changed. With a written recipe, anyone can make the same dish in any kitchen (dev, test, prod), and every edit to the recipe is visible and can be discussed before it reaches the restaurant.

Code

In code

A small but complete databricks.yml:

bundle:
  name: bike_shop_etl

variables:
  catalog:
    description: Catalog the job writes to
    default: dev

resources:
  jobs:
    nightly_rides:
      name: nightly_rides
      schedule:
        quartz_cron_expression: "0 0 2 * * ?"   # 02:00 every day
        timezone_id: UTC
      tasks:
        - task_key: clean_rides
          notebook_task:
            notebook_path: ./src/clean_rides.py
            base_parameters:
              catalog: ${var.catalog}           # filled in per target

targets:
  dev:
    mode: development                      # prefix names, pause schedules
    default: true
    workspace:
      host: https://dev-workspace.example.cloud.databricks.com

  prod:
    mode: production                       # extra safety checks
    git:
      branch: main                          # deploy only from main
    workspace:
      host: https://prod-workspace.example.cloud.databricks.com
    variables:
      catalog: prod
    run_as:
      service_principal_name: "<application-id-of-a-service-principal>"

The everyday commands:

databricks bundle init                # start a new bundle from a template
databricks bundle validate            # check the YAML before deploying
databricks bundle deploy -t dev       # upload code, create/update resources in dev
databricks bundle run -t dev nightly_rides   # start the job now
databricks bundle summary -t dev      # list what this bundle deployed
databricks bundle destroy -t dev      # remove what this bundle deployed

Options

What if I change this?

ChangeEffect
mode: development on a targetResource names get a [dev <user>] prefix and a dev tag; schedules and triggers are paused; pipelines are flagged as development; concurrent runs allowed; deployment lock off.
mode: production on a targetDeploy checks that pipelines aren't in development mode and that you're on the target's Git branch (override with --force). Use a service principal via run_as.
No mode at allAllowed. No presets are applied; you get exactly what the YAML says.
presets on a targetFine-tune individual behaviours, such as name_prefix, trigger_pause_status, tags or jobs_max_concurrent_runs.
Change ${var.catalog} per targetSame code writes to dev or prod catalogs with no edits.
Edit a job in the UI after deployingThe next bundle deploy overwrites your UI change with what the files say. Make changes in the files.
Remove a job from the YAML and deployThe bundle deletes that job from the target, because it no longer appears in the description.

Top-level key

bundle

Name (and optional settings) of the bundle.

Top-level key

resources

Jobs, pipelines, dashboards, serving endpoints, experiments and more.

Top-level key

targets

Where to deploy: workspace, mode, overrides per environment.

Top-level key

variables

Values that change per target, used as ${var.name}.

Top-level key

include

Pull in more YAML files, e.g. resources/*.yml (lesson 01-02).

Top-level key

artifacts

Things to build before deploying, such as a Python wheel (lesson 01-02).

In real life

Real-life scenarios

ScenarioWhat happensFix
Two developers deploy the same job to dev and overwrite each otherNo mode, so both deploy to the same names.Use mode: development: each person gets their own prefixed copy.
A dev deploy starts writing to production tables every nightThe schedule ran and the catalog was hard-coded.Development mode pauses schedules; use a catalog variable per target.
Someone fixes a job in the prod UI; next release undoes itDeploy restores what the files describe.Make the fix in the repo and deploy it.
Prod job fails when its author leaves the companyIt ran as that person, whose access was removed.Set run_as to a service principal in prod.

Exam traps

Exam traps and look-alikes

Trap

"Development mode runs the schedule so you can test it." No: development mode pauses schedules and triggers. Run the job explicitly with bundle run.

Trap

The rename didn't change the CLI: it is still databricks bundle …, and existing databricks.yml files keep working.

Don't confuse

Target (a deployment destination in the bundle) vs deployment mode (development/production presets applied to a target).

Don't confuse

bundle deploy (create or update resources) vs bundle run (start one now). Deploying doesn't run anything by itself.

Check yourself

Quiz

1. You deploy a bundle to a target with mode: development. The job has a daily schedule. What happens at the scheduled time?

Development mode pauses schedules and triggers so personal copies don't run production work. Use bundle run to test.

2. Which file is the main configuration file of a bundle?

databricks.yml holds the bundle name, resources, targets and so on. pyproject.toml describes a Python package.

3. A prod target has mode: production and git.branch: main. You deploy from a feature branch. What happens?

Production mode checks that the current branch matches the target's configured branch.

4. A teammate edits a bundle-deployed job in the UI. What happens at the next bundle deploy?

The files are the source of truth. Deploying makes the workspace match them, overwriting manual edits.

Wrap-up

Key takeaways

  • Bundles describe jobs, pipelines and other resources as YAML next to code: infrastructure as code.
  • databricks.yml has bundle, resources, targets (plus variables, include, artifacts).
  • Development mode: prefixed names, paused schedules. Production mode: branch and pipeline checks, service principal.
  • CLI: validate, deploy, run, destroy. The files win over UI edits.
