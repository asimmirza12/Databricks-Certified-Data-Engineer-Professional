Troubleshooting dependency conflicts

Library problems produce long, scary error messages, but there are only a handful of real causes. Learn to spot which one you are looking at, and the fix usually follows.

The idea

The idea in plain English

A dependency is a library your code needs. Libraries have dependencies of their own, called transitive dependencies. pip's resolver tries to find one version of every library that satisfies everyone's requirements. When no such set exists, you have a dependency conflict.

On Databricks, almost every install failure is one of seven causes:

  1. Version conflict: your library wants a version of something (say numpy) that clashes with another library or with what the runtime or environment already has.
  2. Wrong wheel: the wheel was built for a different Python version or operating system (for example, on a Mac laptop). Databricks compute runs Linux.
  3. Failed build: a source archive needs a compiler or system library that isn't there.
  4. Can't reach the index: the package is on a private index, or network rules block the download.
  5. No permission: the wheel sits in a volume or workspace path the job's identity can't read.
  6. Wrong scope: the library was installed somewhere the failing code can't see (lesson 01-03).
  7. Unsupported method: for example, an init script on serverless, or restarting Python inside a pipeline.

The habit that solves most of them: read the last meaningful line of the error, name the cause, then fix it at the right place (the environment, the wheel build, the index settings, or a grant). And pin versions so the problem can't come back silently.

Planning a dinner party. One guest only eats if there's spicy food, another can't be in a room with spicy food. No menu satisfies both: that's a conflict. Other failures are simpler: the caterer's van can't get through the gate (network), the recipe is in a language the cook can't read (wrong wheel), or the ingredients need an oven you don't have (failed build). Identify which problem you have before changing the menu.

Code

In code

First, find out what is actually installed and what conflicts:

# What versions does this compute have right now?
%pip list | grep -i -E "numpy|pandas|pyarrow"

# Ask pip whether installed packages have broken requirements
%pip check

# Why is a package here, and what does it need?
%pip show report_kit

Then fix it at the right place. A pinned requirements file used by every scope:

# /Workspace/Shared/bike_shop/requirements.txt
geo_fast==3.1.0
report_kit==4.6.2        # 5.x needs numpy>=2, which clashes with geo_fast
# don't list pyspark: Databricks provides it, and installing your own breaks the runtime

Build your own wheel for Linux in CI instead of on a laptop, and check its file name tags:

# In CI (Linux), building a pure-Python package gives a wheel any Python 3 platform accepts
uv build --wheel
ls dist/
# bike_shop_etl-0.3.0-py3-none-any.whl   ← py3 = any Python 3, none = no C code, any = any OS
# geo_fast-3.1.0-cp312-cp312-macosx_14_0_arm64.whl ← Python 3.12 on a Mac only: fails on Linux

A package from a private index, for one dependency (admins can also set a workspace-wide default index):

environments:
  - environment_key: default
    spec:
      environment_version: "4"
      dependencies:
        - --index-url https://pypi.internal.example.com/simple
        - bike_internal_utils==1.4.0

Options

What if I change this?

ChangeEffect
Leave versions unpinnedToday's install works; next month a new release (or a new environment version) resolves differently and breaks the job.
Upgrade a library the runtime depends on (e.g. pyspark, pandas, pyarrow)Can break Databricks' own features. Prefer versions compatible with the preinstalled ones.
Change the serverless environment_versionNew Python version and preinstalled set. Fixes some conflicts, causes others; re-test.
Swap a source archive for a pre-built wheelNo build step at install, so no compiler errors and faster starts.
Set a default package repository (admin)Serverless notebooks, jobs and pipelines use the private index without per-job settings. Index settings in code still override it.
Grant READ VOLUME on the wheel's volumeFixes permission errors for jobs and users installing wheels from that volume.
A wheel that depends on another wheel in a volumepip can't fetch a dependency from a volume path automatically; dependencies must come from an index, or be listed explicitly too.

Where

Serverless

Fix in the environment spec: version, dependencies, environment version. No init scripts.

Where

Pipelines

Fix in the pipeline environment dependencies. No Python restarts inside pipelines.

Where

Bundles

Fix in pyproject.toml, the artifact build, or the job's environments; redeploy.

In real life

Real-life scenarios

ScenarioWhat happensFix
A job that ran for months fails on Monday with a conflictAn unpinned dependency released a new major version over the weekend.Pin it (and its key transitive dependencies) in requirements.
bundle deploy fails in CI with "uv: command not found"The artifact build command needs uv, which the CI machine lacks.Install uv in the CI job before deploying.
A pipeline fails after adding dbutils.library.restartPython()Pipelines don't support restarting Python.Declare the package in the pipeline environment instead of %pip + restart.
Install works for you, fails in the prod jobThe prod job runs as a service principal without READ VOLUME on the wheel's volume.Grant the service principal access to the volume.
A colleague's laptop-built wheel fails on the clusterIt's tagged for macOS.Build wheels in Linux CI, or make the package pure Python.

Exam traps

Exam traps and look-alikes

Trap

"Install the latest version of everything" is rarely the fix. Pinning to compatible versions is.

Trap

On serverless, answers using init scripts, cluster environment variables for proxies, or DBFS library paths are wrong. Use environments and default package repositories.

Don't confuse

ModuleNotFoundError (not installed where the code runs: scope problem) vs ResolutionImpossible (pip couldn't install at all: conflict).

Don't confuse

A platform mismatch (wrong OS/Python tags in the wheel name) vs a version mismatch (wrong library version). Read the wheel's file name.

Check yourself

Quiz

1. Install fails: "geo_fast-3.1.0-cp312-cp312-macosx_14_0_arm64.whl is not a supported wheel on this platform". Best fix?

The file name says macOS on ARM, Python 3.12. Databricks compute runs Linux, so it needs a matching wheel.

2. A serverless job must install from the company's private package index for every job, without editing each job. What fits?

Default package repositories apply to serverless notebooks, jobs and pipelines. Init scripts and compute environment variables don't apply on serverless.

3. "Failed building wheel for fastgeo… command 'gcc' failed". What's going on?

"Failed building wheel" means a source archive was being compiled. Installing a pre-built wheel avoids the build step.

4. Code imports geo_helpers fine in your notebook, but the scheduled job raises ModuleNotFoundError. Most likely cause?

A %pip install lives in your session only. Add the library to the job's environment or task libraries.

5. Which change most reliably stops "it worked last week" dependency breakages?

Pinned versions resolve the same way every time, on every scope, until you deliberately change them.

Wrap-up

Key takeaways

  • Name the cause first: conflict, wrong wheel, failed build, unreachable index, permission, scope or unsupported method.
  • Pin versions; stay compatible with preinstalled core libraries; never install your own pyspark.
  • Prefer Linux-built or pure-Python wheels over source archives.
  • Fix at the right place: serverless/pipeline environments, default package repositories, volume grants, bundle artifacts.
