Stateful streaming and foreachBatch

Some streaming logic must remember things between batches; some sinks can't be written by a plain stream. This lesson covers both: where state lives, and how foreachBatch lets you run any batch code safely on every micro-batch.

The idea

The idea in plain English

A stateless step looks at each row alone (filter, rename, cast). A stateful step needs memory across micro-batches:

  • Aggregations (counts per window), which remember running totals.
  • Deduplication (dropDuplicates, dropDuplicatesWithinWatermark), which remembers keys already seen.
  • Stream-stream joins, which remember rows from each side until a match can arrive.
  • Custom logic with transformWithState: your own per-key state, timers and expiry.

That memory lives in the state store on the executors and is saved with each checkpoint so it survives restarts. On Databricks the RocksDB state store, which keeps state on local disk instead of in memory, is the default on recent runtimes. Watermarks keep state from growing forever.

foreachBatch hands you each micro-batch as an ordinary DataFrame, plus its batch_id. Inside, you can run any batch code: a MERGE INTO upsert, writes to two tables, a write to a database without a streaming connector. It's the standard way to get "update" behaviour into Delta.

The catch: Spark may replay a batch after a failure, and your function runs again. foreachBatch is at-least-once, so you must make it idempotent. For Delta writes, pass txnAppId (a fixed name for this query) and txnVersion (the batch_id); Delta then skips a write it already committed. For MERGE, make the logic safe to repeat: de-duplicate the batch, then upsert by key.

A café's loyalty card is state: the barista must remember how many stamps you have between visits. foreachBatch is the manager who, at the end of every hour, takes that hour's receipts and does whatever bookkeeping is needed: updating the ledger, emailing a supplier. If the manager is interrupted and starts the hour again, each receipt must carry a number so nothing is booked twice.

Code

In code

from delta.tables import DeltaTable
from pyspark.sql import functions as F, Window

APP_ID = "customers_upsert_v1"     # fixed per query; change it if you start a new checkpoint

def upsert_customers(batch_df, batch_id):
    # 1. keep only the latest change per customer in this batch (MERGE fails on duplicate keys)
    latest = (batch_df
        .withColumn("rn", F.row_number().over(
            Window.partitionBy("customer_id").orderBy(F.col("event_ts").desc())))
        .where("rn = 1").drop("rn"))

    # 2. upsert: safe to repeat, because a re-run sets the same values again
    (DeltaTable.forName(batch_df.sparkSession, "bike_shop.silver.customers").alias("t")
        .merge(latest.alias("s"), "t.customer_id = s.customer_id")
        .whenMatchedUpdateAll(condition="s.event_ts > t.event_ts")   # never go backwards
        .whenNotMatchedInsertAll()
        .execute())

    # 3. append to an audit table idempotently: Delta skips (APP_ID, batch_id) it has seen
    (batch_df.select("customer_id", "event_ts", F.lit(batch_id).alias("batch_id"))
        .write.format("delta").mode("append")
        .option("txnAppId", APP_ID)
        .option("txnVersion", batch_id)
        .saveAsTable("bike_shop.silver.customer_audit"))

(spark.readStream.table("bike_shop.bronze.customer_changes")
    .writeStream
    .foreachBatch(upsert_customers)
    .option("checkpointLocation", "/Volumes/bike_shop/silver/_checkpoints/customers_upsert")
    .trigger(availableNow=True)
    .start())

If a batch is written to several sinks, consider batch_df.persist() at the start and unpersist() at the end, so the batch isn't recomputed for each write. In a Lakeflow pipeline, the equivalent is a foreach_batch_sink (Python only; check its preview status in the docs).

Options

What if I change this?

ChangeEffect
MERGE a batch with two rows for the same keyMERGE fails: multiple source rows match one target row. De-duplicate first.
Plain append inside foreachBatch, no txn optionsA replayed batch appends again: duplicates.
Add txnAppId + txnVersion = batch_idDelta skips writes it already committed for that app and version, making appends idempotent.
New checkpoint, same txnAppIdBatch IDs restart from 0, so Delta would skip "already seen" versions: data loss. Use a new app ID with a new checkpoint.
Write to an external database in foreachBatchWorks, but replays repeat it; use upserts keyed on a natural key there.
Stateful operator without a watermarkState grows forever; eventually slow or out of memory.
Change a stateful operator and restart on the same checkpointNot allowed (lesson 01-13).

Exam traps

Exam traps and look-alikes

Trap

foreachBatch is at-least-once. Answers claiming it's automatically exactly-once are wrong; idempotent writes make the results exactly-once.

Trap

Streaming upserts into Delta → foreachBatch + MERGE (or AUTO CDC in a pipeline), not update output mode on a Delta sink.

Don't confuse

foreachBatch (runs your function on a whole micro-batch DataFrame) vs foreach (runs per row: slower, rarely needed).

Don't confuse

txnVersion (Delta write idempotency) vs the Delta table version (its commit number).

Check yourself

Quiz

1. You must upsert streaming changes into a Delta table. Best approach in plain Structured Streaming?

The Delta sink doesn't support update mode; foreachBatch with MERGE gives upsert behaviour.

2. How do you make a Delta append inside foreachBatch idempotent?

Delta records the (app ID, version) pair and skips a repeat write.

3. A MERGE inside foreachBatch fails because two source rows match one target row. Fix?

MERGE needs at most one source row per target key.

4. Which operation is stateful?

Deduplication must remember keys seen in earlier batches. The others look at each row alone.

Wrap-up

Key takeaways

  • Stateful operators (aggregations, dedup, joins, transformWithState) keep state in the state store, saved with checkpoints.
  • Watermarks keep state bounded; RocksDB is the default state store on recent runtimes.
  • foreachBatch runs batch code per micro-batch: MERGE upserts, many sinks.
  • It's at-least-once: de-duplicate, upsert by key, and use txnAppId/txnVersion for idempotent Delta writes.
