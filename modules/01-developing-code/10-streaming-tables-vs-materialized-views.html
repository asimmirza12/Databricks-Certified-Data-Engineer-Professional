Streaming tables vs materialized views

Both keep a table up to date automatically. One processes each new row once and forgets it; the other keeps the answer to a query correct. Picking wrongly gives either stale numbers or a big bill.

The idea

The idea in plain English

A streaming table reads its source as a stream. On each refresh it processes only rows it hasn't seen, appends the results, and never looks back. That makes it cheap and fast, but it assumes the source is append-only: rows are added, never changed or deleted.

A materialized view stores the result of a query and guarantees that, after each refresh, the result matches what the query would return right now. If a source row is corrected or deleted, the view reflects it. To do that it may need to recompute. On serverless, Databricks tries an incremental refresh (work out only what changed); when the query can't be done incrementally, or on classic compute, it does a full recompute.

The rule of thumb:

  • Streaming table: ingestion and row-by-row cleaning of append-only data (files, message buses). Low latency, cost grows with new data only.
  • Materialized view: aggregations, joins, anything that must stay correct when inputs change. Cost depends on how much must be recomputed.

Both can be created inside a pipeline, or on their own from Databricks SQL with a refresh SCHEDULE or TRIGGER ON UPDATE; standalone ones get a serverless pipeline behind the scenes.

A streaming table is a guestbook: each visitor signs a new line, and nobody goes back to edit old lines. A materialized view is the scoreboard at a match: if the referee overturns a goal, the score changes. The guestbook is cheap to keep; the scoreboard must be recalculated when the past changes.

Code

In code

Inside a pipeline (SQL):

-- Append-only ingestion and cleaning: streaming table
CREATE OR REFRESH STREAMING TABLE rides_silver
AS SELECT ride_id, town, price, started_at
FROM STREAM(rides_bronze)
WHERE price > 0;

-- Aggregation that must stay correct: materialized view
CREATE OR REFRESH MATERIALIZED VIEW revenue_by_town
AS SELECT town, SUM(price) AS revenue, COUNT(*) AS rides
FROM rides_silver
GROUP BY town;

Standalone, from Databricks SQL, with a refresh policy:

-- Refresh every hour (a job is created for you)
CREATE OR REPLACE MATERIALIZED VIEW bike_shop.gold.revenue_by_town
  SCHEDULE EVERY 1 HOUR
AS SELECT town, SUM(price) AS revenue FROM bike_shop.silver.rides GROUP BY town;

-- Or refresh whenever an upstream table changes (at most about once a minute)
ALTER MATERIALIZED VIEW bike_shop.gold.revenue_by_town ADD TRIGGER ON UPDATE;

-- A standalone streaming table over files
CREATE OR REFRESH STREAMING TABLE bike_shop.bronze.rides_raw
  SCHEDULE EVERY 15 MINUTES
AS SELECT * FROM STREAM read_files('/Volumes/bike_shop/raw/landing/rides/', format => 'json');

Check the exact SCHEDULE / TRIGGER ON UPDATE syntax in the CREATE MATERIALIZED VIEW reference; clauses are added over time (verify in the docs).

Options

What if I change this?

ChangeEffect
Source rows are updated or deleted under a streaming tableThe stream fails, because the source is no longer append-only.
Stream reads the Delta source with skipChangeCommitsThe stream ignores update/delete commits and keeps going, but the streaming table never reflects those changes.
Aggregation written as a streaming tableAggregates produce updates, not appends, so they belong in a materialized view (stateful streaming aggregates need watermarks; lesson 01-14).
Materialized view on classic computeAlways a full recompute. Incremental refresh needs serverless.
Query uses something incremental refresh doesn't supportFalls back to a full recompute: correct but costlier. The event log's planning information shows which technique was used.
Source is Kafka (no history kept)Use a streaming table. A materialized view can't recompute from a source that forgets old messages.
TRIGGER ON UPDATE on a standalone MVRefreshes soon after upstream tables change, instead of on a fixed timetable.

Pick a streaming table when…

data only arrives (events, files, messages), you want low latency, or the source forgets history.

Pick a materialized view when…

you aggregate or join, inputs can change, or the result must always match its query.

In real life

Real-life scenarios

ScenarioWhat happensFix
Daily revenue built as a streaming table shows wrong totals after refundsRefunds update old rows; the stream never revisits them.Build daily revenue as a materialized view.
A silver streaming table fails after someone ran DELETE on bronzeThe source stopped being append-only.Avoid editing bronze; if deletes are required, use skipChangeCommits knowingly, or an MV.
A materialized view over 3 years of data gets expensive every hourEach refresh is a full recompute (classic compute or an unsupported query).Use serverless and an incremental-friendly query; check planning info in the event log.

Exam traps

Exam traps and look-alikes

Trap

"Lowest latency for append-only events" → streaming table. "Must stay correct when source rows change" → materialized view. Look for which constraint the question stresses.

Trap

Incremental refresh of materialized views is a serverless feature. On classic compute, expect full recomputes.

Don't confuse

Materialized view (stores results, refreshed) vs a regular view (stores nothing, runs the query each time it's read).

Don't confuse

skipChangeCommits (ignore upstream changes and keep streaming) vs AUTO CDC (apply upstream changes properly; next lessons).

Check yourself

Quiz

1. JSON events land every minute and must be queryable within seconds. Which dataset type for ingestion?

Append-only, low-latency ingestion is the streaming table's job.

2. A gold table sums revenue per day; past rides are sometimes refunded (updated). Which dataset type keeps totals correct?

Materialized views reflect upstream updates. A streaming table with skipChangeCommits would just ignore the refunds.

3. A materialized view always fully recomputes, even for tiny changes. What's a likely cause?

Incremental refresh needs serverless and a supported query; otherwise Databricks recomputes fully.

4. Someone deletes rows in a Delta table that a streaming table reads. What happens by default?

Streaming reads expect appends. Use skipChangeCommits to ignore changes, or a different design (MV or AUTO CDC).

Wrap-up

Key takeaways

  • Streaming table: each new row once, append-only source, low latency, cost follows new data.
  • Materialized view: result always matches its query, handles upstream changes, cost follows recompute work.
  • Incremental MV refresh needs serverless and a supported query; otherwise full recompute.
  • Ingest and clean with streaming tables; aggregate and join with materialized views.
