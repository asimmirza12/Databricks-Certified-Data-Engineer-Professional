Checkpoints and exactly-once recovery

Streams crash: machines die, networks blip, code gets redeployed. The checkpoint is what lets a stream pick up exactly where it left off, without losing or doubling a single row.

The idea

The idea in plain English

Structured Streaming is Spark's streaming engine: you write a query as if over a table, and Spark runs it as a series of micro-batches over new data.

Its checkpoint is a folder that records three things:

  • Offsets: before a micro-batch runs, the exact range of source data it will read (e.g. "Kafka partition 0, positions 1,000–1,999" or "these 12 files").
  • Commits: after the batch reaches the sink, a note saying "batch 42 is done".
  • State: for stateful queries (running counts, deduplication, joins), the remembered values between batches.

On restart, Spark reads the checkpoint. If the last batch has offsets but no commit, it crashed midway, so Spark re-runs that same batch with the same offsets. Nothing is skipped.

Re-running could still write twice. That's where the sink matters. Exactly-once results need three parts together: a replayable source (can give back the same data again, like files or Kafka), the checkpoint, and an idempotent sink (writing the same batch twice has the effect of writing it once). The Delta sink is idempotent: it records which batch it already committed and skips a repeat.

Reading a long book in sessions. Before each chapter you write "next: chapter 7, pages 140–162" on a bookmark (offsets). After finishing you tick it (commit). If you fall asleep mid-chapter, you reread from page 140, not from the start and not from page 163. And if your reading notes already say "chapter 7 summarised", you don't write the summary twice (idempotent sink).

Code

In code

# One query = one checkpoint folder, never shared with another query
query = (spark.readStream.table("bike_shop.bronze.ride_events")    # replayable source
    .where("event_type = 'unlock'")
    .writeStream
    .option("checkpointLocation", "/Volumes/bike_shop/silver/_checkpoints/unlocks")
    .trigger(availableNow=True)
    .toTable("bike_shop.silver.unlocks"))                           # idempotent Delta sink

query.awaitTermination()
print(query.lastProgress["batchId"])     # the micro-batch number stored in the checkpoint
# What's inside (look, don't touch)
display(dbutils.fs.ls("/Volumes/bike_shop/silver/_checkpoints/unlocks"))
# commits/  metadata  offsets/  sources/  state/   ← state/ only for stateful queries

In Lakeflow pipelines you never set checkpointLocation: each streaming table's checkpoint is managed for you, and offsets and output are committed together.

Options

What if I change this?

ChangeEffect
Delete the checkpoint and restartThe query starts over from the beginning of the source: rows already written are written again (duplicates), and state is lost.
Two queries share one checkpoint folderThey overwrite each other's progress: lost or repeated data, or failures. Always one checkpoint per query.
Add, remove or change a stateful operation (e.g. change groupBy keys) and restartNot allowed: the stored state no longer matches. Needs a new checkpoint (and a plan for reprocessing).
Change a filter or add a column (stateless change)Usually fine; the new logic applies to batches after the restart.
Add a new source to a queryThe new source starts from its beginning; existing sources resume from their offsets.
Write to a non-idempotent sink (e.g. an API that inserts every call)Replays after crashes create duplicates: you get at-least-once, not exactly-once.
Source can't replay (e.g. data already expired from Kafka)A replay can't fetch the same data again: data loss on recovery. Keep source retention longer than any expected outage.

In real life

Real-life scenarios

ScenarioWhat happensFix
A cluster dies mid-batch; on restart, row counts are correctThe batch was replayed and the Delta sink skipped the half-done write.Nothing to fix: this is the design working.

Exam traps

Exam traps and look-alikes

Trap

A checkpoint alone doesn't give exactly-once. You also need a replayable source and an idempotent sink. Remove either, and you're at-least-once (or worse).

Trap

"Just delete the checkpoint to fix it" usually causes duplicates or data loss. It's a last resort with a rebuild plan.

Don't confuse

Offsets (what a batch will read, written before) vs commits (what finished, written after).

Don't confuse

Streaming checkpoint (query progress) vs Delta checkpoint files in _delta_log (a summary of the table's log).

Check yourself

Quiz

1. A stream crashes after writing batch 42's offsets and output, but before its commit. What happens on restart?

Offsets without a commit mean "planned, not finished", so Spark re-runs exactly that batch.

2. Which combination gives exactly-once results?

Replay needs a source that can give the same data again, the checkpoint to know what to replay, and a sink that ignores repeats.

3. You change the groupBy keys of a streaming aggregation and restart with the same checkpoint. What happens?

Changes to stateful operations aren't allowed between restarts. Use a new checkpoint.

4. Two streaming queries write to different tables but share one checkpoint folder. What's the risk?

Each query must have its own checkpoint location.

Wrap-up

Key takeaways

  • The checkpoint holds offsets (before), commits (after) and state; one folder per query.
  • Offsets without a commit → the same batch is replayed on restart.
  • Exactly-once = replayable source + checkpoint + idempotent sink (Delta is idempotent).
  • Changing stateful logic or deleting the checkpoint breaks recovery; plan a rebuild.
