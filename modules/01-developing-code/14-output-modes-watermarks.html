Output modes and watermarks

Counting rides per 10 minutes sounds easy until a phone in a tunnel uploads its events half an hour late. Watermarks decide how long to wait for stragglers; output modes decide what gets written and when.

The idea

The idea in plain English

Every event has an event time: when it happened (a field in the data). It also has a processing time: when Spark sees it. They differ when data is delayed. Grouping by event time into fixed blocks, like 10:00–10:10, 10:10–10:20, is a tumbling window.

A window's count can change whenever a late event for it arrives, so Spark must keep each open window in state. Without a limit, state grows forever. A watermark sets the limit: "assume events are at most 15 minutes late". Spark tracks the newest event time it has seen and subtracts the delay. Windows that end before that point are final: their state can be dropped, and events older than it are ignored as too late.

The output mode says what each micro-batch writes to the sink:

  • Append (the default): write each result row once, when it's final. With aggregations this needs a watermark, and results appear only after the watermark passes the window's end.
  • Update: write only rows that changed in this batch. A window may be written several times as it grows. The Delta sink doesn't support update mode directly; use foreachBatch with MERGE (next lesson).
  • Complete: rewrite the entire result every batch. Only for aggregations; state is kept forever, so it gets slow as data grows.

A teacher collecting homework. The watermark is the rule "I accept work up to two days late". Until two days have passed, the grade for that assignment can still change (state). After that, the grades are final and late work is refused. Append mode posts each grade once, when final. Update mode re-posts any grade that changed today. Complete mode re-posts the whole grade book every day.

Code

In code

from pyspark.sql import functions as F

rides_per_10min = (spark.readStream.table("bike_shop.bronze.ride_events")
    .withWatermark("event_time", "15 minutes")                # wait up to 15 min for stragglers
    .groupBy(F.window("event_time", "10 minutes"), "town")    # tumbling 10-minute windows
    .count())

(rides_per_10min.writeStream
    .outputMode("append")                                       # each window written once, when final
    .option("checkpointLocation", "/Volumes/bike_shop/gold/_checkpoints/rides_10min")
    .toTable("bike_shop.gold.rides_per_10min"))

Other window shapes and stateful operators that use watermarks:

# Sliding windows: 10-minute windows starting every 5 minutes (overlapping)
F.window("event_time", "10 minutes", "5 minutes")

# Session windows: a ride session ends after 20 minutes without events
F.session_window("event_time", "20 minutes")

# Deduplicate re-sent events, keeping state only within the watermark
events.withWatermark("event_time", "1 hour").dropDuplicatesWithinWatermark(["event_id"])

Append modeEach row written once, after it's final. Works with the Delta sink. Adds latency equal to the watermark delay.
Update modeLower latency: changed rows written every batch. Sink must handle overwrites; Delta needs foreachBatch + MERGE.
Complete modeWhole result rewritten each batch; state kept forever. Only for aggregations; slows as data grows.
Stream-stream joinUse watermarks on both sides (plus a time condition) so join state can be cleaned up. Joins support append mode only.

Exam traps

Exam traps and look-alikes

Trap

"Append mode shows results immediately." Not with windowed aggregations: rows appear only after the watermark passes the window's end.

Trap

The watermark is based on event time in the data, not the clock on the cluster.

Don't confuse

Watermark (how late data may be, controls state and drops) vs trigger (how often a micro-batch runs).

Don't confuse

Update mode (changed rows only) vs complete mode (all rows every time).

Check yourself

Quiz

1. A streaming count per 10-minute window, written to Delta in append mode, never outputs anything. What's missing?

Append mode writes aggregated rows only once they're final, which needs a watermark on the event-time column.

2. The newest event time seen is 10:33 and the watermark delay is 15 minutes. An event with time 10:08 arrives. What happens?

Watermark = 10:33 − 15 min = 10:18. Events older than that are considered too late.

3. Which output mode does the Delta sink NOT support directly?

Delta supports append and complete. For update semantics, use foreachBatch with MERGE.

4. What does raising the watermark delay from 5 to 30 minutes do?

A longer delay waits longer for stragglers: more complete, but more state and more latency in append mode.

Wrap-up

Key takeaways

  • Watermark = newest event time − delay. Older windows are final; older events are dropped; state is cleaned.
  • Append writes final rows once (aggregations need a watermark); update writes changed rows; complete rewrites everything.
  • Delta supports append and complete; use foreachBatch + MERGE for update semantics.
  • Delay is a trade-off: completeness vs state size and latency.
