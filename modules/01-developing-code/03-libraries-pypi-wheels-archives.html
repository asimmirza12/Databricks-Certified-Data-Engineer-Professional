Installing libraries: PyPI, wheels, source archives

The idea

The idea in plain English

A library (or package) is code someone else wrote that you install and import. Python's installer is pip. Libraries come from three kinds of source:

  • PyPI (the Python Package Index): the public online store. pip install requests==2.32.3 downloads from it. Companies often run a private copy, called a private index or mirror.
  • A wheel (.whl): a ready-built package file. Installing it just unpacks files. Fast and predictable. Your own bundle builds one (lesson 01-02).
  • A source archive (.tar.gz, also called an sdist): the package's source code. pip must build it during install, which can need compilers and system libraries, and is slower.

Every compute already has a set of preinstalled libraries: the Databricks Runtime on classic compute, or the environment version on serverless. Your libraries are added on top.

Where you install decides who can see the library. That is its scope:

  • Notebook-scoped (%pip install): this notebook's session only. Gone after a detach or restart.
  • Compute-scoped (cluster libraries): every notebook and job on that classic cluster, reinstalled each time it starts.
  • Serverless environment: the dependency list for a serverless notebook or job task.
  • Pipeline environment: the dependency list in a Lakeflow pipeline's settings, applied to all its source files.

Wheels and requirements files should live in workspace files or Unity Catalog volumes. Storing libraries in the DBFS root is deprecated.

Installing a wheel is buying flat-pack furniture already assembled: carry it in, done. A source archive is the flat-pack box: you need the right tools and time to build it, and a missing screw stops you. PyPI is the furniture shop. Scope is which room you put it in: your own desk (notebook), the whole office (cluster), or the standard kit every new office gets (environment).

Code

In code

Notebook-scoped installs (top of the notebook):

# From PyPI, pinned to an exact version
%pip install geopy==2.4.1

# A wheel stored in a Unity Catalog volume
%pip install /Volumes/bike_shop/libs/wheels/geo_helpers-1.2.0-py3-none-any.whl

# Everything listed in a requirements file kept in workspace files
%pip install -r /Workspace/Shared/bike_shop/requirements.txt

# Restart Python so already-imported modules pick up new versions (not allowed in pipelines)
dbutils.library.restartPython()

A serverless job environment, in a bundle:

environments:
  - environment_key: geo_env
    spec:
      environment_version: "4"                # sets Python version and preinstalled libraries
      dependencies:
        - geopy==2.4.1                        # any line valid in requirements.txt
        - /Volumes/bike_shop/libs/wheels/geo_helpers-1.2.0-py3-none-any.whl
        - -r /Workspace/Shared/bike_shop/requirements.txt

A serverless Lakeflow pipeline, in a bundle:

resources:
  pipelines:
    rides_pipeline:
      name: rides_pipeline
      serverless: true
      environment:
        dependencies:
          - geopy==2.4.1                      # installed at the start of each update

A compute-scoped library on a classic job cluster:

tasks:
  - task_key: enrich
    job_cluster_key: main_cluster
    libraries:
      - pypi: { package: "geopy==2.4.1" }
      - whl: /Volumes/bike_shop/libs/wheels/geo_helpers-1.2.0-py3-none-any.whl

Options

What if I change this?

ChangeEffect
Pin with == (geopy==2.4.1)Same version everywhere. Unpinned packages can resolve differently on different environment versions or days.
Install a source archive instead of a wheelpip must build it at install time: slower, and fails if a compiler or system library is missing.
Put the wheel in a volume or workspace filesRecommended locations, governed by permissions. The reader needs access to that path.
Store the wheel in the DBFS rootDeprecated and disabled by default on modern runtimes.
%pip install in a pipeline source fileLegacy approach. Prefer the pipeline's environment settings, which apply to every source file.
Use an init script to install packagesClassic compute only. Serverless compute and serverless pipelines don't support init scripts.
Change the serverless environment_versionA different Python version and preinstalled library set. Re-test your dependencies.

Exam traps

Exam traps and look-alikes

Trap

A %pip install in a notebook does not make the library available to a job, another notebook, or the next session.

Trap

"Use an init script" is wrong for serverless compute and serverless pipelines: they don't support init scripts. Use environments.

Don't confuse

Wheel (built, install = unpack) vs source archive (must be built during install). Same package, very different install risk.

Don't confuse

Environment version (Databricks' serverless base: Python + preinstalled libraries) vs dependencies (your additions on top).

Check yourself

Quiz

1. A serverless job task needs geopy. Where do you declare it?

Serverless tasks get libraries from their environment spec. Init scripts aren't supported on serverless.

2. Why is a wheel usually safer to install than a source archive?

Installing a wheel just unpacks files. A source archive is built during install, which can fail without the right tools.

3. Where should you store your team's wheel files?

Volumes and workspace files are the recommended, governed locations. DBFS root storage for libraries is deprecated.

4. What is the recommended way to add a PyPI package to a Lakeflow pipeline?

Pipeline environment dependencies apply to all source files and are installed at the start of each update. Pipelines don't support restarting Python.

Wrap-up

Key takeaways

  • Sources: PyPI (or a private index), wheels (pre-built), source archives (built at install).
  • Scopes: notebook (%pip), compute (cluster libraries), serverless environment, pipeline environment.
  • Store wheels and requirements files in volumes or workspace files; DBFS root is deprecated.
  • Pin versions. Serverless and serverless pipelines use environments, not init scripts.
