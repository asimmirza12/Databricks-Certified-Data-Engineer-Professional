Pandas UDFs

When your logic needs Python libraries, pandas UDFs are the fast way in. They hand your function whole batches of rows at once, and the right type can load a model once instead of a million times.

The idea

The idea in plain English

pandas is Python's popular library for tables in memory on one machine. Its column type is a Series; its table type is a pandas DataFrame.

A pandas UDF (also called a vectorized UDF) is a Python function that receives a whole pandas Series of values at a time instead of one value. Spark cuts each partition into batches, sends each batch to Python using Apache Arrow (a fast columnar in-memory format), and your function works on the batch with pandas or numpy. Fewer, bigger hand-offs, and pandas' fast column maths: Databricks quotes up to 100× faster than row-at-a-time Python UDFs.

You pick the type by your function's input and output, written as Python type hints:

  • Series → Series: one value out per value in, like a smarter withColumn.
  • Iterator of Series → Iterator of Series: same result, but your function runs once per partition and loops over batches. Use it when there is expensive setup, such as loading a machine learning model: load once, score every batch.
  • Series → scalar: many values in, one value out. A custom aggregation for groupBy().agg() or window functions.

Related pandas function APIs work on whole DataFrames: applyInPandas runs your function once per group and can return any number of rows; mapInPandas transforms batches of a DataFrame into new batches.

A plain Python UDF is a cashier scanning one item, then walking to the stockroom, then scanning the next. A pandas UDF scans a whole basket at once. The iterator type is a cashier who turns on the till once at the start of the shift (setup) instead of before every basket.

Code

In code

Series → Series: vectorized maths on a column.

import pandas as pd
from pyspark.sql.functions import pandas_udf

@pandas_udf("double")
def km_from_miles(miles: pd.Series) -> pd.Series:
    return miles * 1.60934          # one vector operation for the whole batch; NaN stays NaN

rides = spark.read.table("bike_shop.silver.rides")
rides = rides.withColumn("distance_km", km_from_miles("distance_miles"))

Iterator → Iterator: load a model once per partition, then score every batch.

from typing import Iterator

@pandas_udf("double")
def predict_tip(batches: Iterator[pd.Series]) -> Iterator[pd.Series]:
    model = load_tip_model()             # expensive setup: runs once per partition (your own helper)
    for minutes in batches:              # each item is one Arrow batch as a Series
        yield pd.Series(model.predict(minutes.to_frame()))

rides = rides.withColumn("predicted_tip", predict_tip("minutes"))

Series → scalar: a custom aggregate.

@pandas_udf("double")
def trimmed_mean(prices: pd.Series) -> float:
    low, high = prices.quantile([0.05, 0.95])
    return float(prices[(prices >= low) & (prices <= high)].mean())

rides.groupBy("town").agg(trimmed_mean("price").alias("typical_price"))

applyInPandas: run pandas code per group, returning any number of rows.

def top_two_bikes(pdf: pd.DataFrame) -> pd.DataFrame:
    return pdf.nlargest(2, "price")[["town", "bike_id", "price"]]

top = rides.groupBy("town").applyInPandas(
    top_two_bikes, schema="town string, bike_id string, price double")

Options

What if I change this?

ChangeEffect
Load the model inside a Series → Series functionThe model loads once per batch. Switch to the iterator type to load once per partition.
Raise spark.sql.execution.arrow.maxRecordsPerBatchFewer, bigger batches: less overhead, more memory per call. Lower it if Python workers run out of memory.
Series → scalar or applyInPandas on a skewed keyEach group is loaded fully into one Python worker's memory. One huge group can run out of memory.
Return a Series of a different length (Series → Series)Error: output must be the same length as input.
Declared return type doesn't match the dataArrow conversion errors or wrong values. Declare the real type.
Use a pandas UDF where a built-in existsStill slower than the built-in. pandas UDFs are for logic Spark can't express.

Plain Python UDF

One row per call, simple Python logic, small data or when Arrow types don't fit.

pandas UDF

Batches per call, vectorized pandas/numpy, model scoring. The default choice when Python is needed.

Exam traps

Exam traps and look-alikes

Trap

"Load the model once" points to the Iterator of Series type (or mapInPandas), not Series → Series.

Trap

Grouped pandas operations (Series → scalar, applyInPandas) load each whole group into memory; batch size doesn't split a group.

Don't confuse

pandas UDF (returns a column, used in select/withColumn/agg) vs pandas function API (applyInPandas, mapInPandas: returns a whole DataFrame).

Don't confuse

Arrow-optimized Python UDF (still one value per call, faster transfer) vs pandas UDF (a whole Series per call).

Check yourself

Quiz

1. You must score rows with a model that takes 20 seconds to load. Which type avoids reloading it for every batch?

The iterator type runs your function once per partition, so setup before the loop happens once, then every batch is scored.

2. Why are pandas UDFs faster than plain Python UDFs?

Data still crosses to Python, but in big columnar batches, and pandas processes whole columns at once.

3. You need a custom "trimmed mean" per town in groupBy().agg(). Which type fits?

Series → scalar pandas UDFs define aggregations that reduce a group's values to one result.

4. An applyInPandas grouped by customer fails out-of-memory for one huge customer. Why doesn't lowering maxRecordsPerBatch help?

Each group is passed to your function as one pandas DataFrame. Fix the skew or the grouping key instead.

Wrap-up

Key takeaways

  • pandas UDFs get whole Arrow batches as pandas Series: far fewer calls than plain Python UDFs.
  • Series → Series for column logic; Iterator → Iterator for costly setup like models; Series → scalar for aggregates.
  • applyInPandas (per group, many rows) and mapInPandas (per batch) return DataFrames.
  • Grouped operations hold a whole group in memory: watch for skew. Built-ins still beat all UDFs.
