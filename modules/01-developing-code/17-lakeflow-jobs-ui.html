The idea

The idea in plain English

Lakeflow Jobs (formerly Databricks Workflows, or simply Jobs) is Databricks' orchestrator: it runs pieces of work in order, on a schedule or trigger, and tracks every run.

  • A job is the whole workflow. Each time it runs is a job run.
  • A job holds tasks. Each task does one thing: run a notebook, a Python script or wheel, a SQL query, a Lakeflow pipeline, a dbt project, another job, or control flow like If/else and For each (lesson 01-19).
  • Tasks have dependencies: "clean runs after ingest". Together they form a graph. A task's Run if condition decides whether it runs based on how its upstream tasks ended (default: all succeeded).
  • A trigger starts the job: a schedule, a file arriving in a Unity Catalog location, an upstream table being updated, or continuous (restart as soon as a run ends). You can also run it manually or from the API.
  • Job parameters are key-value settings passed to tasks. Dynamic value references like {{job.run_id}} or {{job.start_time.iso_date}} fill in values at run time.

Each task can have retries (by default most tasks don't retry), a timeout and notifications. Tasks on serverless compute need no cluster settings; on classic compute, tasks can share one job cluster for the run.

A job is a theatre stage manager's cue sheet. Each cue (task) waits for the one before it ("lights after curtain"). The show starts at 8 p.m. (schedule) or when the audience is seated (trigger). If a spotlight fails, the stage manager tries it again (retry), and if the whole show runs long, someone gets a message (notification). Every performance (run) is logged.

Code

In code

You build jobs in the UI (Jobs & Pipelines → Create → Job), but every job is also a JSON definition. This is what the graph above looks like (shortened):

{
  "name": "nightly_bike_shop",
  "schedule": { "quartz_cron_expression": "0 0 2 * * ?", "timezone_id": "UTC" },
  "parameters": [ { "name": "run_date", "default": "{{job.start_time.iso_date}}" } ],
  "max_concurrent_runs": 1,
  "tasks": [
    { "task_key": "ingest",
      "notebook_task": { "notebook_path": "/Workspace/bike_shop/ingest" },
      "max_retries": 2, "min_retry_interval_millis": 60000, "timeout_seconds": 1800 },
    { "task_key": "refresh", "depends_on": [ { "task_key": "ingest" } ],
      "pipeline_task": { "pipeline_id": "<pipeline-id>" } },
    { "task_key": "report", "depends_on": [ { "task_key": "refresh" } ],
      "sql_task": { "file": { "path": "/Workspace/bike_shop/report.sql" }, "warehouse_id": "<warehouse-id>" } },
    { "task_key": "notify", "depends_on": [ { "task_key": "report" } ],
      "run_if": "AT_LEAST_ONE_FAILED",
      "notebook_task": { "notebook_path": "/Workspace/bike_shop/page_on_call" } }
  ],
  "email_notifications": { "on_failure": [ "data-team@example.com" ] }
}

Reading a job parameter inside a notebook task, and passing a value to later tasks:

run_date = dbutils.widgets.get("run_date")                     # job parameters arrive as widgets
rows = spark.read.table("bike_shop.silver.rides").where(f"DATE(started_at) = '{run_date}'").count()
dbutils.jobs.taskValues.set(key="row_count", value=rows)       # later tasks: {{tasks.ingest.values.row_count}}

Options

What if I change this?

ChangeEffect
Retries on a task (default: none for most setups)Transient failures recover automatically. If a timeout is also set, it applies to each attempt.
Run if = All succeeded (default)The task runs only if every upstream task succeeded; otherwise it's marked "Upstream failed".
Run if = At least one failed / All failedFor clean-up or alerting paths; when the condition isn't met the task is "Excluded".
Run if = All doneRuns after upstream tasks finish, whatever happened: good for always-run clean-up.
File arrival triggerThe job starts when new files land in a Unity Catalog volume or external location, instead of on a clock.
Table update triggerStarts when source tables change: no empty runs when nothing new arrived.
Continuous triggerA new run starts as soon as the previous one ends; failures back off exponentially.
max_concurrent_runs (default 1) and queueingLimits overlapping runs; with queueing on, extra runs wait instead of being skipped.
Job-level vs task-level failure notificationsJob-level alerts don't fire on each retried task failure; use task notifications to hear about every failed attempt.

In real life

Real-life scenarios

ScenarioWhat happensFix
A storage hiccup fails the nightly job once a monthNo retries are configured, so one blip fails the run.Add task retries with a short interval.
A clean-up task never runs after failuresIts Run if is the default "All succeeded".Set Run if to "All done".

Exam traps

Exam traps and look-alikes

Trap

"Tasks retry by default." For most configurations they don't; set retries explicitly (serverless jobs have their own auto-optimised retry behaviour, lesson 01-21).

Trap

Old names: Databricks Workflows / Jobs = Lakeflow Jobs. A "Spark job" in the Spark UI is something else entirely.

Don't confuse

Job parameters (set per run, pushed to tasks) vs task values (set by one task at run time, read by later ones).

Don't confuse

Upstream failed (a task skipped because its parents failed) vs Excluded (a failure-path task skipped because nothing failed).

Check yourself

Quiz

1. A clean-up task must run after its upstream tasks finish, whether they succeeded or failed. Which Run if?

"All done" runs once upstream tasks complete, regardless of outcome.

2. A partner uploads files at random times. The job should run only when a file arrives. Which trigger?

File arrival triggers watch a Unity Catalog storage location and start the job when new files land.

3. A task fails once a week on a transient cloud error. Retries aren't configured. What happens?

Without retries the task fails; downstream tasks with the default Run if don't run.

4. How should a task pass a computed row count to a later task?

Task values are designed for passing small results between tasks in a run.

Wrap-up

Key takeaways

  • A job is a graph of tasks with dependencies and Run if conditions (default: all succeeded).
  • Triggers: schedule, file arrival, table update, continuous, manual/API.
  • Set retries, timeouts and notifications deliberately; most tasks don't retry by default.
  • Job parameters and dynamic value references configure runs; task values pass results between tasks.
