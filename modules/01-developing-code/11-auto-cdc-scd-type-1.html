AUTO CDC and SCD Type 1

Source databases send a stream of changes: this row was added, that one changed, another deleted. AUTO CDC turns that stream into an up-to-date table, even when the changes arrive in the wrong order.

The idea

The idea in plain English

Change data capture (CDC) means recording every change made to a source table as an event: an insert, an update or a delete, with the new values and a time or sequence number. A CDC feed is that list of change events.

To turn a CDC feed into a usable table you must, for each event: find the row by its key, then insert, overwrite or delete it. That's an upsert (update if it exists, insert if not) plus deletes. Doing it by hand with MERGE gets hard when events arrive late or out of order, or several changes to one row land in the same batch.

The AUTO CDC API (formerly APPLY CHANGES) does this for you inside a Lakeflow pipeline. You tell it:

  • keys: which column(s) identify a row (e.g. customer_id).
  • sequence_by: which column gives the true order of events (a timestamp or sequence number). The highest value wins, regardless of arrival order.
  • apply_as_deletes: which events mean "delete".
  • stored_as_scd_type: 1 or 2.

SCD means "slowly changing dimension": a table describing things (customers, bikes) whose details change now and then. Type 1 keeps only the latest values: an update overwrites the old row, and history is lost. Type 1 is the default.

A contacts app on your phone. Messages arrive saying "Ana's number is now 555-0102", "delete Ben", "Ana's number is now 555-0101". If the messages come out of order, you'd keep the wrong number. Reading the timestamp on each message and keeping only the newest is sequence_by. Type 1 is the phone overwriting the old number: you can't see what it used to be.

Code

In code

Python, in a pipeline. The target is a streaming table you declare first:

from pyspark import pipelines as dp
from pyspark.sql import functions as F

# bronze: the raw CDC feed (e.g. JSON files from the source database's change log)
@dp.table
def customers_cdc_bronze():
    return (spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("/Volumes/bike_shop/raw/landing/customers_cdc/"))

# silver: one current row per customer
dp.create_streaming_table("customers_silver")

dp.create_auto_cdc_flow(
    target="customers_silver",
    source="customers_cdc_bronze",
    keys=["customer_id"],                              # identifies the row
    sequence_by=F.col("event_ts"),                       # true order of events
    apply_as_deletes=F.expr("op = 'DELETE'"),          # which events delete
    except_column_list=["op", "event_ts"],                # don't copy feed-only columns
    stored_as_scd_type=1                                  # keep latest only (the default)
)

The same in SQL:

CREATE OR REFRESH STREAMING TABLE customers_silver;

CREATE FLOW customers_cdc_flow AS AUTO CDC INTO customers_silver
FROM STREAM(customers_cdc_bronze)
KEYS (customer_id)
APPLY AS DELETE WHEN op = 'DELETE'
SEQUENCE BY event_ts
COLUMNS * EXCEPT (op, event_ts)
STORED AS SCD TYPE 1;

The hand-written alternative is MERGE INTO inside foreachBatch (lesson 01-15), where you must de-duplicate each batch and compare sequence numbers yourself.

Options

What if I change this?

ChangeEffect
Use a column that doesn't reflect true order as sequence_by (e.g. load time)Late events can overwrite newer ones. Use the source's commit time or log sequence number.
Omit apply_as_deletesDelete events are treated as upserts: the row isn't removed (and may get the delete event's values).
ignore_null_updates=TrueNULLs in an update keep the existing values: useful when the source sends only changed columns.
column_list / except_column_listChoose which source columns land in the target (drop op, metadata, etc.).
apply_as_truncatesAn event that empties the whole table. SCD Type 1 only.
Tombstone retention (pipelines.cdc.tombstoneGCThresholdInSeconds, about 2 days by default)How long deleted keys are remembered so late, older updates don't bring them back.
stored_as_scd_type=2Keep history rows instead of overwriting (next lesson).

In real life

Real-life scenarios

ScenarioWhat happensFix
Customer emails flip back to old values now and thenEvents arrive out of order and the pipeline uses arrival order.Use AUTO CDC with sequence_by on the source's change timestamp.
Deleted customers keep reappearing in silverNo apply_as_deletes, so deletes are upserted.Add apply_as_deletes = op = 'DELETE'.

Exam traps

Exam traps and look-alikes

Trap

The target of AUTO CDC must be a streaming table declared in the pipeline (create_streaming_table / CREATE OR REFRESH STREAMING TABLE), not a materialized view.

Trap

Old name: APPLY CHANGES INTO / dlt.apply_changes is now AUTO CDC / dp.create_auto_cdc_flow. Same idea.

Don't confuse

keys (which row) vs sequence_by (which version of that row wins).

Don't confuse

SCD Type 1 (overwrite; current values only) vs Type 2 (new row per change; full history).

Check yourself

Quiz

1. Updates for the same customer sometimes arrive out of order. Which AUTO CDC parameter makes the newest change win?

sequence_by orders events per key; the highest value wins regardless of arrival order.

2. What does SCD Type 1 keep?

Type 1 overwrites in place, so only the latest values remain.

3. Delete events in the feed are not removing rows. What's missing?

Without apply_as_deletes, AUTO CDC treats every event as an upsert.

4. What must the AUTO CDC target be?

AUTO CDC flows write into a streaming table you declare first.

Wrap-up

Key takeaways

  • CDC feeds carry inserts, updates and deletes; AUTO CDC (formerly APPLY CHANGES) applies them in a pipeline.
  • keys pick the row, sequence_by picks the winning version, apply_as_deletes marks deletes.
  • SCD Type 1 (default) overwrites: latest values only.
  • The target is a streaming table; downstream, read it with a materialized view.
