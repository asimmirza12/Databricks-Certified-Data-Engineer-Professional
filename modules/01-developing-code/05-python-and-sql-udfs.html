The idea

The idea in plain English

A UDF (user-defined function) is your own function that Spark calls on each row (or group of rows), used like a built-in function in a query.

First rule: use a built-in function if one exists. Spark has hundreds (upper, round, regexp_extract, date_trunc…). They run inside Spark's engine, the optimizer understands them, and Photon can speed them up.

When you do need your own, there are two simple kinds:

  • A SQL UDF, written as a SQL expression with CREATE FUNCTION … RETURN …. Spark can fold the expression straight into the query plan, so it runs about as fast as built-in functions.
  • A Python UDF, a Python function wrapped with @udf. Spark's engine runs on the JVM (the Java runtime), not Python. So each row must be serialized (converted into bytes), sent to a separate Python process, run, and sent back. That round trip, row by row, makes Python UDFs the slowest option. Using Apache Arrow for the transfer (useArrow=True) cuts that cost a lot.

A UDF can be temporary (lives in your session only) or permanent, stored in Unity Catalog as catalog.schema.function so others can use it with a grant. Lesson 01-07 covers permanent Unity Catalog functions in depth.

Built-in functions are staff who speak the office language and work at their desks. A SQL UDF is a new written procedure the same staff can follow: just as fast. A Python UDF is a specialist in another building who speaks a different language: every single form must be translated, walked over, processed and walked back. Arrow is sending the forms in one big box instead of one at a time.

Code

In code

Built-in first. Often you don't need a UDF at all:

from pyspark.sql import functions as F

rides = spark.read.table("bike_shop.silver.rides")
banded = rides.withColumn("band",
    F.when(F.col("minutes") < 15, "short")
     .when(F.col("minutes") < 45, "medium")
     .otherwise("long"))            # NULL minutes fall through to "long": decide if that's right

A SQL UDF, permanent in Unity Catalog:

CREATE OR REPLACE FUNCTION bike_shop.silver.price_band(minutes INT)
  RETURNS STRING
  COMMENT 'Short, medium or long ride'
  RETURN CASE
    WHEN minutes IS NULL THEN NULL
    WHEN minutes < 15 THEN 'short'
    WHEN minutes < 45 THEN 'medium'
    ELSE 'long' END;

SELECT ride_id, bike_shop.silver.price_band(minutes) AS band FROM bike_shop.silver.rides;

-- A temporary version, for this session only
CREATE TEMPORARY FUNCTION price_band_tmp(minutes INT) RETURNS STRING
  RETURN CASE WHEN minutes < 15 THEN 'short' ELSE 'long' END;

A Python UDF, when the logic truly needs Python (here, a library call):

from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

@udf(returnType=StringType(), useArrow=True)   # Arrow speeds up the transfer
def station_slug(name):
    if name is None:                             # always handle NULL: it arrives as None
        return None
    import unicodedata
    ascii_name = unicodedata.normalize("NFKD", name).encode("ascii", "ignore").decode()
    return ascii_name.lower().replace(" ", "-")

stations = spark.read.table("bike_shop.silver.stations")
stations.withColumn("slug", station_slug("station_name"))

# Make it callable from SQL in this session
spark.udf.register("station_slug", station_slug)
spark.sql("SELECT station_slug(station_name) FROM bike_shop.silver.stations")

Options

What if I change this?

ChangeEffect
Replace a Python UDF with a built-in expressionUsually much faster; the optimizer and Photon can work on it.
Python UDF → SQL UDFLogic is inlined into the plan, no Python process involved. Only possible if the logic is expressible in SQL.
useArrow=True on a Python UDFData moves in Arrow batches instead of pickled rows: less serialization overhead. Newer Spark versions enable this by default.
Forget to handle None in a Python UDFNULL inputs raise a Python error that fails the whole task, or produce wrong output.
Wrong returnTypeValues that don't match the declared type can silently become NULL (or error, depending on settings). Declare the type you really return.
CREATE TEMPORARY FUNCTION vs CREATE FUNCTION catalog.schema.nameTemporary: this session only, no grants. Permanent: stored in Unity Catalog, shareable with EXECUTE.

Decision 1

Built-in exists?

Use it. Stop here.

Decision 2

Expressible in SQL?

SQL UDF. Fast and shareable.

Decision 3

Needs Python?

Prefer a pandas UDF; plain Python UDF (with Arrow) for simple per-row logic.

Exam traps

Exam traps and look-alikes

Trap

A question asks for the most performant option, and a built-in function can do the job: the built-in wins over any UDF.

Trap

Python UDFs are opaque to the optimizer: it can't push filters through them or reason about their output.

Don't confuse

spark.udf.register (makes a Python UDF callable in SQL, this session only) vs CREATE FUNCTION catalog.schema.f (permanent, governed, shareable).

Don't confuse

SQL UDF (logic in SQL, inlined) vs a Python UDF called from SQL (still runs in Python, still slow).

Check yourself

Quiz

1. Why is a plain Python UDF usually slower than a SQL UDF doing the same logic?

The engine runs on the JVM. Each row is converted and shipped to Python and back. SQL UDFs stay in the engine and are inlined.

2. Several teams need the same price-band logic, written in SQL, with access control. Best choice?

Permanent Unity Catalog functions are shared by name and governed. Registered and temporary functions live in one session.

3. A Python UDF fails when the input column contains NULL. What's the right fix?

NULL arrives as None in Python. Handle it explicitly (or filter NULLs first). Arrow changes transfer speed, not logic.

4. What does useArrow=True change for a Python UDF?

Arrow-optimized Python UDFs exchange data in columnar batches. The function still runs in Python and stays opaque to the optimizer.

Wrap-up

Key takeaways

  • Order of preference: built-in → SQL UDF → pandas UDF → plain Python UDF.
  • Python UDFs ship rows to a Python worker and back; Arrow (useArrow) reduces the cost.
  • SQL UDFs are inlined into the plan and can be permanent, governed Unity Catalog functions.
  • Handle NULLs and declare the correct return type.
